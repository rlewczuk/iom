# Encode the tensor release-or-quarantine protocol once behind a shared registry helper and one registry-state definition

**Order:** 62
**Priority:** P1 — consolidates the most lifetime-critical protocol in the project into one source of truth; required but gates no other remediation. Deliberately ordered after the registry-shape redesign (61-AR-003) and the backend behavior fixes (55, 58) so the helper is written once against the final registry and quarantine shapes instead of being implemented against an obsolete one.
**Blocked by:** `55-ST-001-harden-sycl-queue-lifetimes`, `58-ST-004-unify-quarantine-allocation-failure`, `61-AR-003-simplify-outstanding-work-registry`
**Source:** `docs/changes/0001-tensor-view/review.md` — `AR-002`
**Review severity:** medium
**Review verification:** verified, confidence 95

## Outcome

The snapshot → fence-outside-locks → classify → release-or-quarantine protocol exists exactly once, as `iom::detail::release_or_quarantine(registry, address, make_cleanup, release)` beside `OutstandingWorkRegistry` in `include/iom/detail/outstanding_work_registry.hpp`. Each of the five tensor destructors (CPU, CUDA, ROCm, SYCL, TTNN) shrinks to its null-address early return plus one helper call carrying two backend closures: a cleanup-construction closure (allocator `AllocatorCleanupAction` with or without the CUDA/ROCm `activate` pre-release hook; TTNN's post-58 swallow-and-leak `TtnnNativeCleanupAction`) and a release closure (`release_aligned_storage` with or without the activate hook; TTNN's `planes_->clear()` under the API mutex). The four byte-identical registry-state headers of the registering backends (CUDA, ROCm, SYCL, TTNN's boilerplate half) collapse into one shared `detail::RegistryState` definition with `allocate_queue_id` and `register_copy_entries`; CPU's reduced post-61 state struct stays as 61-AR-003 delivered it (CPU registers nothing, so its shape legitimately differs). The completion-side twins that remain after 61-AR-003's CPU opt-out — `SequenceOutcome` and the release-vs-invalidate resolution in the CUDA/ROCm/SYCL/TTNN `complete_task` bodies — collapse into a shared `detail::SequenceOutcome` and `detail::release_or_invalidate_entries`, with each queue retaining only its fence-success policy line. Observable behavior — which storage is freed, deferred, or quarantined; free counts; token/wait semantics; teardown and drain ordering — is unchanged on every backend, and the 58-ST-004 swallow-and-leak allocation-failure policy is preserved verbatim.

## Requirements

1. **Helper body** — `release_or_quarantine` reproduces the established protocol statement-for-statement, with no null-address check (callers own their early returns; TTNN intentionally has none, so a null address still takes the `snapshot_for` throw → cleanup-only path today):
   1. `std::vector<OutstandingWorkRegistry::EntrySnapshot> snapshots;` (post-61 the alias of `Entry`) filled inside `try { snapshots = registry.snapshot_for(address); } catch (...) { make_cleanup(); return; }` — on snapshot failure the storage is quarantined and **no entries are removed** (there are no snapshot IDs), matching all five destructors today. The always-empty CPU registry after 61-AR-003's opt-out exercises this body with zero snapshots and reaches `release()` directly.
   2. Fence loop, outside every registry lock: `snapshot.state == EntryState::Invalidated || !snapshot.fence` sets `safe_to_release = false` and skips invocation; otherwise `snapshot.fence()` inside `try` — a throw, `!result.succeeded`, or a non-null `result.failure` marks unsafe; all other snapshots are still invoked.
   3. Safe branch: for each snapshot, `registry.remove_entry_if_present(snapshot.id, address)` — the same `address` value captured on entry, replacing today's `const void* original_address` + `const_cast` pattern — then `release()`, then return.
   4. Unsafe branch: `make_cleanup()` first (it makes the storage unreachable), then the same `remove_entry_if_present` loop. Quarantine-before-removal ordering is load-bearing: a racing `complete_task` must observe removed entries, not double-owned storage.
   - The helper is `noexcept`; the closures are invoked inside it, so any closure escape terminates exactly as today's `noexcept override` destructors do. Both closure parameters are unconstrained templates constrained only by `std::invocable` (the `include/iom/detail/aligned_storage.hpp` convention); no `std::function` erasure is introduced on these paths.
2. **Backend cleanup closures** (the `make_cleanup` argument) — each is `noexcept`, captures what today's lambda captures, and preserves its backend's exact behavior:
   - CPU and SYCL: `try { quarantine.emplace<detail::AllocatorCleanupAction>(allocator_, address_, view().spec().tiled_storage_nbytes()); } catch (...) { /* intentional leak */ } address_ = nullptr;` — the null-out runs whether or not the emplace threw; no `pre_release` hook (CPU has no activate; SYCL has no context-activation requirement).
   - CUDA and ROCm: identical plus the `AllocatorCleanupAction` pre-release hook `[device = &device_] { device->activate(); }`.
   - TTNN: the post-58-ST-004 lambda verbatim — `std::unique_ptr<std::vector<ttnn::Tensor>> retained(planes_.release())` (null-check no-op return), one `try` constructing the `std::function` finish temporary and the `TtnnNativeCleanupAction` node followed by `state_->quarantine.add(std::move(action))`, and a `catch (...)` clause running `(void)retained.release();`. The two failure classes this absorbs are distinct and must not be conflated: **(a) construction failure** (pre-move — the `std::function` temporary or the action node's `operator new` throws) leaves `*retained` still owning the planes, so the catch's `(void)retained.release();` is what leaks them; **(b) recording failure** (post-move — 61-AR-003's vector-backed `Quarantine::add` throws on `push_back` growth) happens after `std::move(action)` transferred ownership, so `retained` is already null and the caller's catch cannot leak anything it no longer holds; `add` itself releases-and-leaks the by-value action node (which owns the planes) before rethrowing, per 61-AR-003 Requirement 5. Both classes land in the same observable swallow-and-leak contract that 58-ST-004 records in parent-spec §7 ("constructing **or recording** the quarantine cleanup action fails inside a `noexcept` tensor destructor, the storage is deliberately leaked"): the destructor returns normally, the storage is neither freed nor returned to the runtime, no quarantine entry is recorded, and the process continues.
3. **Backend release closures** (the `release` argument) — each is `noexcept`: CPU/SYCL `iom::detail::release_aligned_storage(allocator_, address_)`; CUDA/ROCm the same call with the `[this] { device_.activate(); }` pre-release argument; TTNN `std::lock_guard<std::mutex> lock(device_.api_mutex()); planes_->clear();`.
4. **Destructor shape** — each of the five destructors keeps its `noexcept override` and its existing early return (`address_ == nullptr` on the four allocator backends; none on TTNN), then makes exactly one `release_or_quarantine` call. The bodies between the early return and the call contain no protocol logic beyond computing closure captures (e.g. `bytes`). TTNN passes `planes_->data()` as the address.
5. **Shared registry state** — `detail::RegistryState`, `detail::allocate_queue_id`, and `detail::register_copy_entries` in the registry header are the only registry-state definitions for the registering backends; `src/cuda/registry_state.hpp`, `src/rocm/registry_state.hpp`, `src/sycl/registry_state.hpp`, and `src/ttnn/registry_state.hpp`'s boilerplate are deleted, every use site (device registry-state members and accessors, queue `state_` members, `make_queue`/`make_*_queue` signatures) uses `detail::RegistryState`, and no compatibility alias (`using CudaRegistryState = ...`) remains. `src/cpu/registry_state.hpp` stays exactly as 61-AR-003 delivered it — the two-member struct without id counters or helpers, which are dead weight on a backend that registers nothing; `~CpuTensor` consumes it through the helper unchanged. All backend includes of the registry header use the post-61 path `"iom/detail/outstanding_work_registry.hpp"`. `register_registry_entries`, `allocate_registry_queue_id`, and the 57-ST-003 rollback contract in `register_entry` are untouched.
6. **Completion glue** — `detail::release_or_invalidate_entries(registry, outcome, failure)` builds `std::array<EntryId, 2>{outcome.source_entry_id, outcome.destination_entry_id}`; when `failure || !outcome.fence_succeeded` it calls `registry.invalidate_entries(entries)` and returns `false`; otherwise `(void)registry.try_release_entry(...)` on both IDs and returns `true`. Each `complete_task` keeps its outcome pop block and per-queue `outcome_mutex_`/`outcomes_` map and its policy. The shared `detail::SequenceOutcome` is the map's value type for CUDA, ROCm, and TTNN; **SYCL is not identical** and uses a backend-local wrapper (below), so the four `complete_task` bodies are not collapsed into one policy:
   - CUDA and ROCm: keep `outcome.fence_succeeded = !failure && !outcome.retained_failure;` before the resolver — algebraically equivalent to today's `if (failure || outcome.retained_failure)`. Their post-enqueue signal is the `retained_failure` member staged by `execute`.
   - post-55 SYCL: 55-ST-001 step (e) delivered a **flat** SYCL-local outcome — `SequenceOutcome{source_entry_id, destination_entry_id, std::shared_ptr<SyclFenceState> state}` — distinct from CUDA/ROCm/TTNN because `StagedWorker`'s `FenceComplete` callback returns `void` and the shutdown drain skips `fence_complete` entirely, so the retained post-enqueue failure cannot travel back through the callback and must be readable from the outcome's own `state`. This task restructures that flat SYCL outcome into a backend-local wrapper that nests the shared `detail::SequenceOutcome` (so the two entry ids live in the common half the resolver consumes) and keeps the state alongside it:
     ```cpp
     struct SyclSequenceOutcome {
         iom::detail::SequenceOutcome common;          // the two entry ids (+ fence_succeeded/retained_failure fields this task keeps)
         std::shared_ptr<SyclFenceState> state;        // the cached, race-safe fence outcome
     };
     ```
     `SyclQueue::complete_task(sequence, callback_failure)` then: (1) pops the `SyclSequenceOutcome` under `outcome_mutex_`; (2) calls `outcome.state->result()` to read the cached `detail::FenceResult` (idempotent — it combines the event wait with any failure stored via `set_failure(...)` on the post-enqueue path); (3) combines `fence_result.failure` with `callback_failure` into one `combined_failure` `std::exception_ptr` (the cached retain wins when set, so the post-enqueue path dominates); (4) sets the resolver inputs from that result — `outcome.common.fence_succeeded = fence_result.succeeded && !fence_result.failure;` — and calls `release_or_invalidate_entries(state_->registry, outcome.common, /*failure=*/static_cast<bool>(callback_failure))`; (5) calls `DeviceOps::complete(sequence, combined_failure)` exactly once, which is what makes repeated `wait(oid)` rethrow the retained post-enqueue failure. Reducing SYCL to `!failure && !outcome.retained_failure` (the CUDA/ROCm line) would silently drop the retained failure, because SYCL's outcome carries no such member — the failure lives inside `SyclFenceState`. Task 60 may extend `SyclFenceState` (metadata-slot release) but not this ownership shape.
   - TTNN: keeps `finish_native`-based `fence_result` computation and `outcome.fence_succeeded = fence_result.succeeded && !fence_result.failure;`, then uses the resolver's return value: `if (!released && !failure) { failure = fence_result.failure; }` and `if (released) { last_finished_seq_.store(sequence, std::memory_order_release); }` — exactly today's branch bodies. `fence_succeeded` itself stays (AR-006, not this task, owns unread-field cleanup).
   - `execute`-side outcome staging and rollback are unchanged in behavior: CUDA's retained-failure staging and fence-resource destroy stay as-is, and SYCL's pre-enqueue/post-enqueue branches from 55-ST-001 step (f) keep their exact rollback semantics. The only edits are mechanical — CUDA/ROCm/TTNN rename their outcome type to `detail::SequenceOutcome`, and SYCL's step (e) constructs the new `SyclSequenceOutcome{ detail::SequenceOutcome{source_entry_id, destination_entry_id}, task.state }` wrapper (copying, not moving, `task.state`, per 55-ST-001) in place of the flat outcome it built before. No registration, sequence, token, or rollback ordering changes.
7. **No observable change:** free/release/quarantine decisions, exception categories, token and wait semantics, sequence consumption, queue-destructor ordering (`invalidate_entries_for_queue` → `shutdown_and_drain` → native teardown), device-destructor quarantine drain (SYCL's pre-context-reset drain per 55-ST-001 included), and registry/quarantine unit-test behavior are all identical to the pre-change tree.
8. **Common-header hygiene:** the registry header gains no backend include and no backend type; the helper and state definitions compile for every backend translation unit from the one header. Public API (`Device`, `Tensor`, `TensorView`, `Allocator`, `DeviceOps`) and public headers are unchanged.
