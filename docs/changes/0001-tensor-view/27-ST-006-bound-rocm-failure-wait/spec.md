# Bound the ROCm failure-path `wait` on a possibly errored stream

**Order:** 27
**Priority:** P1 — hypothesis-grade bounded ROCm failure-path waitability defect that, if it materializes on the target HIP version, can cause `wait` to hang even after `commit_failure` has stored the failure
**Blocked by:** None
**Source:** `docs/changes/0001-tensor-view/review.md` — `ST-006`
**Review severity:** low
**Review verification:** hypothesis, confidence 60

## Outcome

Once `RocmQueue::copy` has detected a post-enqueue submission failure on plane 1, the worker (`RocmQueue::run`) reaches `complete(sequence, failure)` in bounded time without ever calling `hipEventRecord` or `hipEventSynchronize` against the errored stream. Failed work stores its failure in `pending_failures_` (the existing `commit_failure` slot), the queue advances its task/token so the caller receives a valid `oid`, and `wait(oid)` rethrows the stored failure deterministically within a 5-second subprocess watchdog. The watchdog re-execs the test binary via `posix_spawn`/`execve` with `IOM_ROCM_WATCHDOG_CHILD=1` set in the child's environment; the child process runs the **entire** fault-injection setup (constructs the `RocmDevice` and `RocmQueue`, calls `inject_submission_fault_for_testing`, submits `queue->copy`, calls `queue->wait`, exits with status 0 on caught `std::runtime_error` or status 1 on no-throw). The parent test only spawns, polls, kills, and reaps. No iom state — not the queue, not the oid, not `pending_failures_` — crosses the fork boundary; queue IDs and pending failure state are process-local, so the child must construct its own queue and submit its own copy. On timeout the parent sends `SIGKILL`, reaps via `waitpid(pid, &status, 0)`, and calls `std::exit(2)` to terminate the test process. The fix has exactly one design path: do not record a completion event for the failed sequence; route the failure through the queue's failure lane and let the worker call `complete` directly.

## Current failure

The hypothesis (review verification: hypothesis, confidence 60) is that the ROCm failure path can leave `wait` blocked indefinitely even after the catch block has already stored the failure through `commit_failure`. The shape is:

`RocmQueue::copy` (`src/rocm/copy.hip:389-435`) installs the retained-failure branch so that, after the first `hipLaunchKernelGGL` of `launch_copy_plane`, a `check_hip("HIP kernel launch", hipGetLastError())` failure or a `record_event` failure captures `std::current_exception()` and calls `commit_failure(sequence, failure)` at `src/rocm/copy.hip:432`. Before calling `commit_failure`, the catch block performs:

```cpp
(void)hipEventRecord(event_guard.event, stream_);
```

The intent is to keep the worker `run()` loop (`src/rocm/copy.hip:517-555`) consistent across success and failure paths — every committed sequence must have an event the worker can `hipEventSynchronize`. The problem is that `stream_` may be in an error state on the failure path: when the very first `hipLaunchKernelGGL` of `launch_copy_plane` reports `hipGetLastError() != hipSuccess`, or when `record_event` fails, the stream has an outstanding asynchronous error. `hipEventRecord` against an errored stream is documented to return an error, which the code discards with `(void)`. The worker then enters `run()`, calls `hipEventSynchronize(task.event)`, and the semantics of that synchronize call on an event recorded against an errored stream are not part of any published contract: on some ROCm versions it returns immediately with the stream error; on others it blocks. If it blocks, `RocmQueue::run` is wedged on `hipEventSynchronize`, the `failure` already stored via `commit_failure` is never surfaced, and `wait(oid)` hangs despite the failure having been retained. Note that `hipEventSynchronize` accepts no timeout argument and cannot itself bound the wait; the only way to bound the wait is to never call `hipEventSynchronize` on the failed-sequence path.

The review explicitly marks this hypothesis-grade and notes that the exact behavior is ROCm-version-dependent. The fix must therefore remove the dependency on "the event will eventually complete in bounded time" from the failure path entirely and route the failure into the worker through the same `complete(sequence, failure)` shape every other retained failure uses — without ever recording an event on the errored stream and without ever calling `hipEventSynchronize` for that sequence.

The CUDA analogue (`src/cuda/copy.cu:441-444`) repeats the same `(void)cudaEventRecord(event_guard.event, stream_)` pattern; the review does not flag it as hypothesis-grade because CUDA's runtime contract around errored streams is closer to a known synchronous-error return. This task is ROCm-only; see the Non-goals.

## Scope

- In `src/rocm/copy.hip`, change the post-link retained-failure branch inside the `RocmQueue::copy` submit callback so that the failed sequence **does not record a completion event** and so the failed-sequence `Task` already pushed to `staged_` is reused (not duplicated). The chosen design is single-path: the success-path code at `src/rocm/copy.hip:411-415` already pushed `Task local{sequence, event_guard.event}` into `staged_` under `mutex_` and set `event_guard.linked = true` before the `try` block. The catch block must therefore, under the same `mutex_`, **find that existing staged entry by `sequence`** (the lambda's `sequence` capture is unique per in-flight submission) and set its `event` member to `nullptr`; it must **not** push a second `Task{sequence, nullptr}` and must **not** call `hipEventRecord`. After nulling the staged entry's event, the catch sets `event_guard.linked = false` so `PendingEvent::~PendingEvent` destroys the created `hipEvent_t` exactly once on lambda scope exit (the existing RAII guard at `src/rocm/copy.hip:53-62` already destroys `event` when `linked == false`). The catch then calls `commit_failure(sequence, failure)` to record the captured `std::current_exception()`. When the lambda returns, the existing post-submit `publish_staged()` (called at `src/rocm/copy.hip:435`) splices the single null-event entry from `staged_` to `tasks_` under `mutex_`. The worker (`RocmQueue::run`) drains `tasks_`; for entries whose `event == nullptr` it skips `hipEventSynchronize` and `hipEventDestroy` entirely and calls `complete(task.sequence, nullptr)`, which lets `DeviceOps::complete` read `pending_failures_[sequence]` and route the stored failure into `failures_[sequence]`. The successful-path entries keep their existing shape (event created, event recorded, event synchronized, event destroyed in the worker).
- Every queued `Task` carries exactly one owner for its event: on the success path the worker (or the destructor drain) owns the event and calls `hipEventDestroy`; on the failure path `PendingEvent` owns the event and calls `hipEventDestroy` on lambda scope exit after the catch sets `event_guard.linked = false`. No event is destroyed twice, no event leaks. `RocmQueue::run` has exactly two task shapes: an entry with `event == nullptr` (failure path) and an entry with a non-null `event` (success path). The null branch skips `hipEventSynchronize` and `hipEventDestroy` and calls `complete(task.sequence, nullptr)`, which lets `DeviceOps::complete` consume `pending_failures_[sequence]` and route it into `failures_[sequence]`. The non-null branch keeps the existing `check_hip("hipEventSynchronize", ...)` + `hipEventDestroy(task.event)` + `complete(task.sequence, failure)` shape unchanged, with `hipEventDestroy(task.event)` owned by the worker in this branch. The hypothesis-grade concern is the post-enqueue path where the stream is already errored before any event is recorded; the chosen design removes the event from that path so the concern cannot materialize.
- The CUDA `CudaQueue::copy` catch block and `CudaQueue::run` are **not** modified by this task (see Non-goals).
- The fault-injection contract (`SubmissionFault::event_record`, `SubmissionFault::third_plane_launch`) is unchanged: the existing `inject_submission_fault_for_testing` entry point at `src/rocm/copy.hip:567-570` still drives the same fault points, and `record_event` (`src/rocm/copy.hip:64-71`) still returns `hipErrorInvalidValue` from the same path. The fix consumes the fault at the catch-block boundary instead of letting it reach `hipEventRecord` on the errored stream.
- The conformance test for "ROCm submission remains transactional across post-enqueue failures" (`test/rocm/test_rocm_conformance.cpp:382-505`) is extended with a deterministic bounded-wait regression assertion: `wait(oid)` must rethrow the stored `std::runtime_error` within 5 seconds, and the test fails by **process exit** (not by a CHECK) if the 5-second budget is exceeded. The bound is enforced by a subprocess watchdog: the parent test calls `posix_spawn` (or `fork`+`execve`) on the same test binary with `IOM_ROCM_WATCHDOG_CHILD=1` set in the child's environment. The child runs the entire fault-injection setup (constructs the `RocmDevice` and `RocmQueue`, calls `inject_submission_fault_for_testing` with the configured `SubmissionFault`, submits `queue->copy`, calls `queue->wait`, exits with status 0 on caught `std::runtime_error` or status 1 on no-throw). No iom state crosses the fork boundary; the child constructs its own queue because queue IDs and pending failure state are process-local. The parent polls `waitpid(pid, &status, WNOHANG)` once per 100 ms up to 50 iterations (5 seconds total). On child exit before the budget the parent inspects `WEXITSTATUS(status)` / `WIFSIGNALED(status)`. On timeout the parent sends `SIGKILL` to the child PID, calls `waitpid(pid, &status, 0)` to reap the zombie, prints the diagnostic, then calls `std::exit(2)` to terminate the test process. The repeated-wait assertion (via the existing in-process `expect_repeated_runtime_failure` helper) is kept in the parent process; it does not need a subprocess because it does not bound the wait.
- The retained-failure contract from spec 19 (`docs/changes/0001-tensor-view/19-ST-002-transactional-cuda-rocm-submission/spec.md`) — `copy` returns a valid `oid`, `wait(oid)` rethrows the stored failure on every call — is preserved unchanged.

The deterministic bounded-wait regression test enforces the 5-second budget via a subprocess watchdog: the parent test re-execs the same test binary via `posix_spawn` (or `fork`+`execve`) with `IOM_ROCM_WATCHDOG_CHILD=1` set in the child's environment; the child process runs the full fault-injection setup (constructs the `RocmDevice` and `RocmQueue`, calls `inject_submission_fault_for_testing`, submits `queue->copy`, calls `queue->wait(token)`) and exits with status 0 on caught `std::runtime_error` or 1 on no-throw; the parent enforces the 5-second budget by polling `waitpid(pid, &status, WNOHANG)` and `SIGKILL`+`waitpid` on timeout (see Verification). The result is one event → one destroy, no double-destroy, no leak.

The new conformance case asserts that `wait(oid)` rethrows within 5 seconds on these two paths.

- The bounded-wait regression test uses a subprocess watchdog (`posix_spawn`/`fork`+`exec` in the parent; `waitpid(WNOHANG)` polling; `SIGKILL`+`waitpid` on timeout; `std::exit(2)` to terminate the test process on timeout). It does **not** use `std::async`/`std::future`/`std::thread` to bound the wait, because any future/thread that calls `queue->wait` cannot be safely torn down while the waiter is blocked: a `std::async` future's destructor joins its task and would re-introduce the hang the watchdog is supposed to bound; a `std::thread` would require either `pthread_cancel` (which is unsafe at arbitrary cancellation points and is not part of POSIX mandatory cancellation) or detaching (which leaks the queue and races with the parent's destruction). The subprocess watchdog is the only design that (a) cannot destroy the queue while the waiter runs, (b) enforces a hard upper bound on `wait` duration, and (c) lets the test process exit non-zero on timeout.

## Cross-finding coordination

The existing tests at `test/rocm/test_rocm_conformance.cpp:417-432` (`expect_repeated_runtime_failure(*queue, launch_failure)` and `expect_repeated_runtime_failure(*queue, record_failure)`) are authoritative. After `SubmissionFault::third_plane_launch` and `SubmissionFault::event_record`, `copy` **must** return a non-zero `oid` (CHECK_NE(launch_failure, 0) at line 420; CHECK_EQ on `iom_conformance::token_sequence`) and a later `wait(token)` **must** rethrow the stored `std::runtime_error`. There is no post-link throw rollback, no sequence reclaim, no `submit` rollback that re-throws the original exception out of `copy`. The retained-failure protocol is the contract: `copy` returns the encoded token, `commit_failure` records the failure under `pending_failures_[sequence]`, and `wait(oid)` consumes it. **AR-002 (`docs/changes/0001-tensor-view/30-AR-002-share-backend-queue-scaffold/spec.md`) is blocked by this spec and must preserve the null-fence retained-failure protocol exactly once when its `iom::detail::StagedWorker<Task>` helper lands.** Concretely, AR-002's helper must expose the four-step protocol as one shape that every backend uses:

1. **Single staged entry** — the composing backend queue's `execute` callback pushes exactly one `Task` into the helper's `staged_` before the first backend enqueue (matching the existing per-backend pre-AR-002 shape at `src/rocm/copy.hip:413-415`, `src/cuda/copy.cu:475-477`, `src/cpu/device.cpp:284-287`, `src/ttnn/device.cpp:284-292`). On a post-link failure the executor closure does **not** push a second `Task`. The single staged entry is the only entry the worker and destructor will see for this sequence.
2. **Post-link `execute` closure sets `task.fence = nullptr` and calls `this->commit_failure(sequence, std::current_exception())`, then returns normally.** In the post-AR-002 code, the helper's `Task` carries an existing `event` member (preserved verbatim from the current per-backend source — `hipEvent_t` for ROCm at `src/rocm/copy.hip:462`, `cudaEvent_t` for CUDA at `src/cuda/copy.cu:521-525`, etc.) **plus one new field `void* fence = nullptr` that AR-002 introduces**. The `void* fence` member is the **authoritative** nullable handle for the post-AR-002 protocol: on a post-link failure, the executor closure writes `task.fence = nullptr` (in addition to leaving the existing `event` member's RAII guard to destroy the native handle exactly once) and calls the composing backend queue's protected `DeviceOps::commit_failure(sequence, std::current_exception())` helper directly via the captured queue pointer. The helper call stores the failure in `DeviceOps::pending_failures_[sequence]` (`src/iom.cpp:594-602`). The executor closure returns normally; `submit` returns the encoded `oid`; `copy` returns it to the caller; no exception propagates out of `copy` on the post-link failure path. **No fifth callback is introduced.** The helper's `Callbacks` struct has exactly four `std::function` members — `execute`, `fence_complete`, `fence_destroy`, `complete` — and no fifth. There is no per-task `std::exception_ptr failure` field on `Task` (the helper does not retain per-task failures; the executor closure retains post-link failures by calling the captured-`this` `commit_failure` directly).
3. **Publish** — the helper's `publish_staged` runs after `execute` returns. The single staged entry moves from `staged_` to `tasks_` under `mutex_` via `tasks_.splice(tasks_.end(), staged_)`. On the post-link failure path the staged entry's `fence == nullptr`; on the success path the staged entry's `fence` is the executor's recorded native handle. `publish_staged` is non-throwing.
4. **Helper worker gates callbacks on `fence`** — the helper's `run()` worker loop, on each popped task, checks `if (current.fence != nullptr)` before calling `callbacks_.fence_complete(current.fence)`; it always calls `callbacks_.fence_destroy(current.fence)` and `callbacks_.complete(current.sequence, failure)`, with the **explicit gate that `fence_destroy` is skipped when `current.fence == nullptr`**. The non-null `fence` branch keeps the existing per-backend `fence_complete`/`fence_destroy` shape (CUDA `cudaEventSynchronize` + `cudaEventDestroy`, ROCm `hipEventSynchronize` + `hipEventDestroy`, CPU/TTNN no-op). The null `fence` branch skips both `fence_complete` and `fence_destroy`, calls `callbacks_.complete(current.sequence, /*failure=*/nullptr)`, and `DeviceOps::complete` consumes the previously-stored `pending_failures_[sequence]` into `failures_[sequence]` so `wait(oid)` rethrows. **No `hipEventSynchronize` and no fence destroy is ever invoked on a null fence.**

The helper's `shutdown_and_drain` and the worker shutdown-drain iterate both `staged_` and `tasks_` and call `callbacks_.fence_destroy(entry.fence)` **only when `entry.fence != nullptr`**, then `callbacks_.complete(entry.sequence, /*failure=*/nullptr)`, in that order — exactly as the existing per-backend destructor drains do today (`src/cuda/copy.cu:435-444`, `src/rocm/copy.hip:371-385`). The pre-link throw path (executor throws before `fence` is recorded) erases the staged entry under the lock and ST-007's `submit` rollback at `include/iom/iom.hpp:106-114` reclaims the reservation; the conformance invariant (throw without consuming a sequence; next successful `copy` returns sequence `2`) is preserved.

**Distinction between pre-AR-002 and post-AR-002 references in this spec.** The Scope, Implementation references, Requirements, and Acceptance criteria sections above describe the current pre-AR-002 ROCm code and use the existing `event` field name (the nullable `hipEvent_t event` on `RocmQueue::Task` at `src/rocm/copy.hip:460-463`). The Cross-finding coordination section above describes the post-AR-002 future code and uses the authoritative `void* fence` field name that AR-002 introduces. Both the pre-AR-002 fix and the post-AR-002 helper preserve the same observable contract: `copy` returns a valid `oid`, `wait(oid)` rethrows the stored `std::runtime_error`, no `hipEventSynchronize` / fence_complete runs on a null-fence entry, every `hipEvent_t` is destroyed exactly once, no exception propagates out of `copy` on the post-link failure path. The four-step protocol above is the contract between this spec and AR-002.


## Non-goals

- Modifying `src/cuda/copy.cu` or `src/cuda/copy.hpp`. The CUDA analogue carries the same `(void)cudaEventRecord` pattern, but the review explicitly does not flag it; CUDA's errored-stream semantics are not in scope for this finding.
- Modifying `include/iom/iom.hpp`, `src/iom.cpp`, the `DeviceOps::submit`/`wait`/`complete`/`commit_failure` interfaces, the queue-ID pool, or the sequence bit layout.
- Changing the CUDA, CPU, or TTNN queue implementations.
- Synchronously draining the stream before throwing. This task shortens the failure path through the worker; it does not introduce a new throw site.
- Claiming or using a HIP API timeout for `hipEventSynchronize` (none exists). The bounded-wait guarantee is structural: the worker does not call `hipEventSynchronize` on the failed-sequence path, and the regression test enforces a hard upper bound on `wait(oid)` independently.
- Implementing a CUDA-side analogue of this fix. The hypothesis is ROCm-specific.
- Replacing the `hipEvent_t` lifetime fence with a different fence mechanism. The event remains the only fence for queued work on the success path.
- Adding a public "cancel" operation, cross-queue dependencies, or any implicit waiting in `~DeviceOps`.
- Promoting the failure-routing fix through `add`, `mul`, `silu`, `linear`, `rmsnorm`, or `sdpa`, all of which reject with capability `std::runtime_error` before submission.
- Cross-cutting refactors of the queue scaffolding (spec 19's retained-failure contract is preserved verbatim; this is a narrow, ROCm-local boundary change).
- Branching the worker into more than two task shapes (success with event, failure without event). The chosen design has exactly one failure-path shape: a `Task` whose event is null and whose failure lives in `pending_failures_[sequence]`.
- Rejected alternatives, recorded for clarity:
  - A sibling `failure_task_` list draining parallel to `tasks_` is rejected: the chosen design keeps a single `tasks_` container with a nullable `event` member, so the worker's drain loop and the destructor's drain loop iterate one container.
  - A `std::optional<hipEvent_t>` member on `Task` is rejected: a plain nullable `hipEvent_t event` with `nullptr` meaning "no event" is sufficient and matches the established C-style HIP handle idiom.
  - Letting the worker call `hipEventSynchronize` on a null-event `Task` is rejected: `hipEventDestroy(nullptr)` is undefined behavior and `hipEventSynchronize` accepts no timeout argument; the null branch must skip both calls entirely.
  - Letting the worker call `hipEventSynchronize` on a non-null event and route a non-`hipSuccess` return into a per-task `failure` is rejected: this is the prior design's failure-routing shape and is what the review flagged as hypothesis-grade. The post-enqueue failure path is removed instead of being routed around.
  - Pushing a second `Task{sequence, nullptr}` from the catch block is rejected: the success-path code at `src/rocm/copy.hip:411-415` already pushed the single `Task{sequence, event_guard.event}` for this sequence, and the worker must see exactly one entry per sequence. A second push would either (a) be drained after `publish_staged` and cause the worker to call `complete` twice on the same sequence, breaking `DeviceOps::complete`'s `sequence >= next_sequence_` invariant (`src/iom.cpp:578`), or (b) leak the original staged entry past the publish, where the destructor would destroy the same event the catch's `PendingEvent` already destroyed. The chosen design reuses the existing staged entry.
  - Bounding the `wait` with `std::async`/`std::future` is rejected: the future's destructor joins its task, which re-introduces the hang the watchdog is supposed to bound.
  - Bounding the `wait` with a `std::thread` and `pthread_cancel` is rejected: `pthread_cancel` is unsafe at arbitrary cancellation points (the waiter may hold `completion_mutex_` mid-`wait`) and is not part of POSIX mandatory cancellation.
  - Bounding the `wait` with a detached `std::thread` is rejected: it leaks the queue and races with the parent's destruction.

## Acceptance criteria

- [ ] The post-link catch block in `src/rocm/copy.hip:RocmQueue::copy` contains no `hipEventRecord` call and pushes no second `Task`. The success-path code at `src/rocm/copy.hip:411-415` already pushed a single `Task{sequence, event_guard.event}` into `staged_`; the catch walks `staged_` under `mutex_`, finds the entry whose `sequence` matches the lambda capture, sets that entry's `event` member to `nullptr`, sets `event_guard.linked = false`, and calls `commit_failure(sequence, std::current_exception())`. `PendingEvent::~PendingEvent` destroys the event exactly once on lambda scope exit. `publish_staged()` at `src/rocm/copy.hip:435` then moves the single null-event entry from `staged_` to `tasks_`.
- [ ] No duplicate-completion, no double-destroy. The worker (`RocmQueue::run` at `src/rocm/copy.hip:517-555`) calls `complete(task.sequence, ...)` exactly once per sequence: the worker null branch fires on the null-event entry published by the catch, calls `complete(task.sequence, nullptr)` so `DeviceOps::complete` consumes `pending_failures_[sequence]`, and increments `completed_`. No second `Task` with the same sequence is ever pushed. The event created at `src/rocm/copy.hip:404-409` is destroyed exactly once: on the failure path by `PendingEvent::~PendingEvent`; on the success path by the worker's `hipEventDestroy(task.event)` in the non-null branch. The destructor at `src/rocm/copy.hip:361-390` never destroys an event twice because (a) the failure path's event was already destroyed in the lambda, (b) the success path's event was already destroyed by the worker, and (c) any drain-time null-gated `if (entry.event != nullptr)` check short-circuits before the destroy.
- [ ] The bounded-wait regression test uses a subprocess watchdog implemented by re-execing the same test binary via `posix_spawn` (preferred) or `fork`+`execve` with `IOM_ROCM_WATCHDOG_CHILD=1` set in the child's environment. The child's `main()` checks `getenv("IOM_ROCM_WATCHDOG_CHILD")` first; if set, the child runs the full fault-injection entry point — constructs the `RocmDevice` and `RocmQueue` from scratch, calls `inject_submission_fault_for_testing` with the configured `SubmissionFault` (the parent cannot inject the fault for the child; fault-injection state is process-local), submits `queue->copy(...)`, calls `queue->wait(token)`, catches `std::runtime_error`, and calls `_exit(0)` on caught or `_exit(1)` on no-throw. The parent test (inside its `TEST_CASE`) calls `posix_spawn` with `IOM_ROCM_WATCHDOG_CHILD=1` in `envp`, polls `waitpid(pid, &status, WNOHANG)` once per 100 ms up to 50 iterations, total 5 seconds. On child exit before the budget the parent inspects `WEXITSTATUS(status)` / `WIFSIGNALED(status)`. On timeout the parent sends `SIGKILL` to the child PID, calls `waitpid(pid, &status, 0)` to reap the zombie, prints the diagnostic, then calls `std::exit(2)` to terminate the test process. The test process exits non-zero on timeout — it does not merely record a failed doctest `CHECK` before a `std::async` future's destructor joins the still-blocked waiter. No `std::async` / `std::future` / `std::thread` is used to bound the wait. No iom state — not the queue, not the oid, not `pending_failures_` — crosses the fork boundary.
- [ ] `queue->wait(token)` on a token whose sequence was committed via `SubmissionFault::third_plane_launch` rethrows within 5 seconds on the target ROCm version. The conformance test fails by **process exit** if the 5-second budget is exceeded; the bound is enforced by the subprocess watchdog above, not by a HIP API timeout (`hipEventSynchronize` has no timeout argument) and not by a `std::async` future. The child process asserts this contract end-to-end (inject, submit, wait, exit 0 on caught): the parent's contract is that the child exits with status 0 within 5 seconds.


- [ ] `RocmQueue::run` branches on `task.event == nullptr` after popping the task: the null branch skips `hipEventSynchronize` and `hipEventDestroy` entirely and calls `complete(task.sequence, /*failure=*/nullptr)`, which lets `DeviceOps::complete` route the previously-stored `pending_failures_[sequence]` into `failures_[sequence]`. The non-null branch keeps the existing `check_hip("hipEventSynchronize", ...)` + `hipEventDestroy` + `complete` shape. No third branch exists.
- [ ] `queue->wait(token)` on a token whose sequence was committed via `SubmissionFault::event_record` rethrows within 5 seconds. Repeated `wait(token)` invocations on the same token rethrow the same `std::runtime_error` with the same `what()` string via `expect_repeated_runtime_failure`. The bounded-wait assertion uses the subprocess watchdog above; the repeated-wait assertion uses the in-process `expect_repeated_runtime_failure` helper (no subprocess needed for that path).

- [ ] The destructor drain at `src/rocm/copy.hip:361-390` iterates both `staged_` (the `while (!staged_.empty())` block at `:373-376`) and `tasks_` (the `while (!tasks_.empty())` block at `:377-380`) in that order. For each entry, the destructor's `hipEventDestroy(entry.event)` call is gated by `if (entry.event != nullptr)` so it never calls `hipEventDestroy(nullptr)`. For each entry, the destructor calls `complete(entry.sequence, /*failure=*/nullptr)` so `DeviceOps::complete` consumes any stored `pending_failures_[sequence]` and records the failure in `failures_[sequence]`. The worker outer-catch drain at `src/rocm/copy.hip:547-554` adopts the same null-gated destroy and same per-entry `complete` call. The destructor remains `noexcept`-friendly: it swallows driver errors with `(void)` casts as today.

- [ ] Grep `src/rocm/copy.hip` for `hipEventRecord` and confirm exactly one call site remains: the success-path `record_event(event_guard.event, stream_)` call inside the `try` block at `src/rocm/copy.hip:425-426`. No `hipEventRecord` call remains inside the post-link catch block at `src/rocm/copy.hip:419-433`.
- [ ] Grep `src/rocm/copy.hip` for `hipEventSynchronize` and confirm exactly one call site remains, on the non-null branch of `RocmQueue::run` after `if (task.event == nullptr) { ... } else { check_hip("hipEventSynchronize", hipEventSynchronize(task.event)); ... }`. The null branch never reaches `hipEventSynchronize`.
