# Remove dead queue and pool state so stored state matches real invariants

**Order:** 65
**Priority:** P1 — required local state cleanup after the shared staging-pool extraction (63-AR-004) and the shared release-or-quarantine helper (62-AR-002), both operating against the registry/quarantine shape 61-AR-003 finalized. Verified low-severity finding that gates no other work.
**Blocked by:** `62-AR-002-share-release-quarantine-protocol`, `63-AR-004-share-cuda-rocm-copy-infrastructure`
**Source:** `docs/changes/0001-tensor-view/review.md` — `AR-006`
**Review severity:** low
**Review verification:** verified, confidence 92

## Outcome

Every field the CUDA/ROCm staging pools and the queue task/outcome records store is either read by production code or removed. The shared policy-parameterized `iom::detail::StagingSlotPool<Policy>` carries no unread context/ordinal identity in its constructor or members; the CUDA and ROCm queued tasks hold caller view pointers only inside the synchronous `execute()` window and never afterwards; `iom::detail::SequenceOutcome::fence_succeeded` is deleted because no code stores it — each `complete_task` computes its `bool fence_succeeded` from its existing per-backend derivation (CUDA/ROCm/SYCL/TTNN each keep their own logic intact) and passes that value as an argument to the shared `iom::detail::release_or_invalidate_entries`. Quarantine recording failures (post-61 `Quarantine::add` throws on vector growth after the action moves in) leak the action node through the add function's own absorption; construction failures (pre-move, including 58-ST-004's TTNN node allocation) continue to leak via the existing caller catch. Observable behavior — copy results, fences, failure retention, quarantine, and pool allocation accounting — is unchanged.

## Current failure

Three classes of stored state are never read, and each misrepresents an invariant:

1. **Unread pool identity.** Both `StagingSlotPool` instances accept a context/ordinal at construction and store it in a private member that no method reads. After 63-AR-004 consolidates the twins into the single `iom::detail::StagingSlotPool<Policy>` definition in `src/shared/staging_pool.hpp`, the merged template still takes that parameter (the backend-specific shape — `CUcontext` on CUDA, `int device_ordinal` on ROCm, unified via `Policy::context_type`) and still carries a private member that nothing reads. Allocations run through `Policy::staging_allocate(bytes)` / `Policy::staging_free_noexcept(pointer)` (the post-63 shared surface), which allocate on the caller's already-active context/device — no stored identity is consulted. The dead member implies staging is bound to the constructing context, inviting future code to be "fixed" against an invariant the allocation path never had.
2. **Dead task view pointers.** `CudaQueue::Task::source/destination` and `RocmQueue::Task::source/destination` are raw pointers into the caller's `copy(const TensorView&, TensorView&)` parameters. `execute()` runs synchronously inside `StagedWorker::submit_copy` (`include/iom/iom.hpp:81`) on the submitting thread — `DeviceOps::submit` invokes the work lambda inline (`include/iom/iom.hpp:320`) — and reads the views for the post-63 shared `detail::copy_metadata_layout(source, destination)`, `detail::write_copy_metadata(host, source, destination)`, the `source.native_handle()` / `destination.native_handle()` arguments to `detail::launch_grid_stride_copy<gpu_policy>`, the registry registration addresses, and the rollback. After `execute()` returns, the task is spliced into `tasks_` (`include/iom/iom.hpp:95`) and the worker's `process()` reads only `fence` and `sequence` (`include/iom/iom.hpp:136-155`). The published task therefore carries dangling caller-stack pointers for its entire asynchronous lifetime, falsely implying queued tasks dereference caller views asynchronously. The real asynchronous contract is storage-based: entries registered during `execute()` capture addresses plus a fence, and tensor destruction is gated by the 49-ST-003 registry — never by host view pointers.
3. **Unread outcome flag.** `iom::detail::SequenceOutcome::fence_succeeded` (defined in `include/iom/detail/outstanding_work_registry.hpp` by 62-AR-002 — the shared struct holds only `source_entry_id`, `destination_entry_id`, `retained_failure` after this task) is written by every `complete_task` and read by the shared `detail::release_or_invalidate_entries` resolver. Storing it on the outcome makes the value live twice (once on the outcome, once as the resolver's input); the resolver should be passed the value directly, not consult the struct. The CUDA/ROCm queues (which use the shared `detail::SequenceOutcome` directly with `retained_failure` as their post-enqueue signal) derive the bool as `!failure && !outcome.retained_failure` and pass it as the resolver's new third argument. The post-55 SYCL queue is the wrapper case: it declares `SyclSequenceOutcome { iom::detail::SequenceOutcome common; std::shared_ptr<SyclFenceState> state; }`, populates `outcomes_` keyed by sequence with that wrapper, and the cached fence completion lives on the wrapper's `state` field. The TTNN queue uses the shared `detail::SequenceOutcome` directly with `finish_native`'s `fence_result.succeeded && !fence_result.failure` (combined with `outcome.retained_failure`) as its derivation. The SYCL derivation is the load-bearing case: `complete_task` must read the cached `FenceResult` from `outcome.state->result()`, derive the bool from `fence_result.succeeded && !fence_result.failure`, AND propagate the cached `fence_result.failure` (combined with `callback_failure`) through `DeviceOps::complete` so the caller's `wait(oid)` rethrows the retained post-enqueue failure. The resolver's bool does NOT depend on `combined_failure`; the propagated `exception_ptr` and the resolver bool share one source of truth (`state->result()`) but feed two distinct sinks. Reading `state->result()` only to derive a bool and discarding the cached retain would break the wait-rethrow guarantee task55/62 establishes.

Impact is local confusion cost — maintainers reason about invariants the code does not have. No behavioral defect.
