# Commit the submission sequence before `queue_work` runs in `DeviceOps::submit`, roll back on synchronous `queue_work` failure, and update `commit_failure` to accept any reserved-but-not-completed sequence

**Order:** 28
**Priority:** P1 — latent whole-codebase contract gap in the common submission boundary that turns into a spurious `std::invalid_argument` if any future `queue_work` completes inline, compounded by a now-incompatible `commit_failure` guard
**Blocked by:** None
**Source:** `docs/changes/0001-tensor-view/review.md` — `ST-007`
**Review severity:** low
**Review verification:** hypothesis (latent — no current backend completes inline), confidence 75

## Outcome

`DeviceOps::submit` reserves the next sequence number under `completion_mutex_`, increments `next_sequence_` to commit the reservation, and only then invokes the backend's `queue_work` callable. A backend whose `queue_work` synchronously calls `DeviceOps::complete(sequence)` is guaranteed to satisfy `complete`'s `sequence < next_sequence_` guard rather than tripping the `sequence >= next_sequence_` throw. If `queue_work` throws before returning, `submit` catches the exception and rolls the reservation back **only when both** `next_sequence_ == sequence + 1` (no later submission has reserved a sequence since) **and** `completed_ < sequence` (the failing `sequence` has not already been completed by an inline `complete(sequence)` that preceded the throw); if either condition fails, the reservation stands and `submit` rethrows the original exception verbatim. The `completed_ < sequence` clause is required to preserve the completion invariant `completed_ <= next_sequence_ - 1`: an unconditional `next_sequence_ = sequence` after an inline `complete(sequence)` that was followed by a throw would corrupt the invariant and make future `wait`/`complete`/`commit_failure` calls on later sequences invalid. ## Current failure

`DeviceOps::submit` (`include/iom/iom.hpp:83-100`; definition in the header) currently does:

```cpp
template <typename QueueWork>
oid submit(QueueWork queue_work) {
    std::uint64_t sequence = 0;
    {
        std::lock_guard<std::mutex> lock(completion_mutex_);
        if (next_sequence_ > kMaxSequence) {
            throw std::overflow_error(
                "DeviceOps 56-bit submission sequence is exhausted");
        }
        sequence = next_sequence_;
    }
    queue_work(sequence);
    {
        std::lock_guard<std::mutex> lock(completion_mutex_);
        ++next_sequence_;
    }
    return encode_token(sequence);
}
```

`next_sequence_` is advanced only **after** `queue_work` returns. The hypothesis (review verification: hypothesis, confidence 75 — no current backend completes inline) is that a future backend whose `queue_work` synchronously calls `DeviceOps::complete(sequence)` would trip `DeviceOps::complete`'s guard at `src/iom.cpp:578-581`:

```cpp
if (sequence >= next_sequence_) {
    throw std::invalid_argument(
            "completion of a sequence that was never submitted");
}
```

because `sequence == next_sequence_` at the moment of the inline `complete` call. The throw would escape from inside `submit`'s `queue_work(sequence)` invocation, propagate out through `submit`, and the caller would see `std::invalid_argument("completion of a sequence that was never submitted")` rather than a waitable token. The four current backends all stage their work into a per-queue deque and only mark the sequence complete on a worker thread, so the path is unreachable today — but the doc-comment invariant at `include/iom/iom.hpp:74-82` ("the sequence is consumed only when queue_work returns") only documents the current backend behavior; it does not enforce a contract that an inline-completing backend could rely on.

Naively moving `++next_sequence_` ahead of `queue_work` breaks `DeviceOps::commit_failure` (`src/iom.cpp:596-610`):

```cpp
void DeviceOps::commit_failure(
        std::uint64_t sequence, std::exception_ptr failure) {
    if (sequence == 0) {
        throw std::invalid_argument("retained failure sequence is zero");
    }
    if (!failure) {
        throw std::invalid_argument("retained failure is empty");
    }
    std::lock_guard<std::mutex> lock(completion_mutex_);
    if (sequence != next_sequence_) {
        throw std::invalid_argument(
                "retained failure is not for the active submission");
    }
    pending_failures_[sequence] = std::move(failure);
}
```

Under the new reservation order, when the post-link catch block at `src/cuda/copy.cu:491-495` runs `commit_failure(sequence, failure)` from inside `queue_work`, `next_sequence_ == sequence + 1`, so the existing guard `sequence != next_sequence_` is true and `commit_failure` throws `std::invalid_argument("retained failure is not for the active submission")`. That `std::invalid_argument` escapes from inside `queue_work` and is caught by `submit`'s new rollback handler, which then rethrows it as the visible error — replacing the captured backend failure (`std::runtime_error` from a CUDA driver wrapper) with a spurious `std::invalid_argument`. The same shape applies to the ROCm post-link catch at `src/rocm/copy.hip:432`. The earlier ST-007 draft that proposed `sequence + 1 == next_sequence_` would still reject this case under concurrent `submit`: if a later `submit` has already reserved a sequence (`next_sequence_ > sequence + 1`) while the failing `queue_work` is still running, the original `sequence != next_sequence_` guard's replacement is still false for a gap larger than zero, and `commit_failure` would still throw — replacing the captured backend failure with a spurious `std::invalid_argument`. The fix must therefore widen `commit_failure`'s acceptance window to any reserved-but-not-completed sequence, defined precisely as `sequence < next_sequence_ && sequence > completed_`, where `completed_` is the high-water mark of sequences that have already reached `complete()` (`include/iom/iom.hpp:136`; updated by `DeviceOps::complete` at `src/iom.cpp:590-592`).

The review explicitly flags the underlying finding as hypothesis-grade because no current backend completes inline. The fix must be small and surgical: reserve the sequence number up front, roll back on synchronous `queue_work` failure when no later submission has reserved, and update `commit_failure`'s guard to accept any reserved-but-not-completed sequence — preserving the existing `std::invalid_argument` rejection category for never-submitted and already-completed tokens.

## Scope

- Change `DeviceOps::submit` (`include/iom/iom.hpp:83-100`) so that `next_sequence_` is incremented **before** `queue_work(sequence)` runs. The chosen shape is a single critical section that both reads and reserves: read `next_sequence_`, check `> kMaxSequence`, assign `sequence`, and `++next_sequence_` together; only then call `queue_work(sequence)` outside the lock. If `queue_work(sequence)` throws, `submit` catches the exception, takes `completion_mutex_` again, and rolls back the reservation **only when** `next_sequence_ == sequence + 1 && completed_ < sequence` (no later reservation has happened AND the failing `sequence` has not already been completed, e.g. by an inline-completing backend that then threw past `complete`); otherwise the reservation stands and the exception propagates unchanged via `throw;`. The extra `completed_ < sequence` clause preserves the completion invariant `completed_ <= next_sequence_ - 1` so that future `wait`/`complete`/`commit_failure` calls on later sequences remain valid.
- Change `DeviceOps::commit_failure` (`src/iom.cpp:596-610`) so its guard accepts **any reserved-but-not-completed sequence**, not only the latest one. The new guard is exactly `sequence < next_sequence_ && sequence > completed_`: reserved (strictly below `next_sequence_`, the exclusive upper bound of reserved sequences) and not already completed (strictly above `completed_`, the inclusive upper bound of completed sequences). The conjunction is overflow-safe: `completed_ <= next_sequence_ - 1` (invariant maintained by `complete` at `src/iom.cpp:578-592`) and `sequence <= next_sequence_ - 1` (by the reserved half), so both sides of `sequence > completed_` are in `[0, kMaxSequence]` and the comparison is well-defined for `std::uint64_t`. Rejections:
  - `sequence == 0` → `std::invalid_argument("retained failure sequence is zero")` (unchanged).
  - `!failure` → `std::invalid_argument("retained failure is empty")` (unchanged).
  - `sequence >= next_sequence_` → `std::invalid_argument("retained failure is not for a reserved submission")` (updated message text; describes the never-submitted case).
  - `sequence <= completed_` → `std::invalid_argument("retained failure is for a sequence that has already been completed")` (new rejection; describes the already-completed misuse case).
  - Otherwise: `pending_failures_[sequence] = std::move(failure);` (unchanged).
- The 56-bit sequence-exhaustion `std::overflow_error` throw in `submit` stays positioned **before** `queue_work` runs (the guard must trip before the backend sees the sequence number, matching the existing doc comment). Because the reservation has not yet happened at the exhaustion site, the rollback path never sees the exhausted state.
- Pre-`queue_work` validation failures raised by `submit` itself before the critical section — none exist today because `submit`'s only synchronous check is the exhaustion guard, which throws before reservation — throw with no sequence consumed, exactly as today. Pre-`queue_work` validation failures raised **inside** the backend's `queue_work` callable — `validate_copy`, `identical_window`, `plane_pairs`, `view_planes`, `cudaEventCreateWithFlags`/`hipEventCreateWithFlags` failing on the post-link path, the TTNN extent guard — now run **after** the reservation, so they hit the rollback branch (`next_sequence_ == sequence + 1 && completed_ < sequence` in the single-threaded call shape used by every backend today; `completed_ < sequence` holds because no `complete(sequence)` has run yet) and the next successful submission returns the expected sequence number, e.g. sequence 2 after a failing `SubmissionFault::event_create` at `test/cuda/test_cuda_conformance.cpp:372-379`.
- `DeviceOps::complete` (`src/iom.cpp:572-594`), `DeviceOps::wait` (`src/iom.cpp:546-570`), and `DeviceOps::seek_next_sequence` (`src/iom.cpp:612-618`) are not modified. The `complete` guard `sequence >= next_sequence_` remains as the rejection criterion for never-submitted sequences; the fix changes only the value of `next_sequence_` at the moment an inline `complete` would observe it, not the guard itself. The `wait` guard `sequence >= next_sequence_` likewise stays. The `seek_next_sequence` precondition `next_sequence == 0 || next_sequence < next_sequence_` is unaffected by the change. `DeviceOps::complete`'s read-and-erase of `pending_failures_` at `src/iom.cpp:582-586` is unchanged and continues to drain the entry `commit_failure` stored; it is the worker that owns the `complete` call, after the `Task` has been drained from the queue's per-backend task list.
- `encode_token` and the queue-ID pool are not modified.
- The retained-failure contract from spec 19 (`docs/changes/0001-tensor-view/19-ST-002-transactional-cuda-rocm-submission/spec.md`) is preserved verbatim for the post-link branch that has already linked the task into `staged_`: the backend's queue_work catches its own exception, calls `commit_failure(sequence, failure)`, and lets `submit` return normally with the encoded token. The new `commit_failure` guard accepts any reserved-but-not-completed sequence in the half-open interval `(completed_, next_sequence_)`; the post-link catch sees the just-reserved sequence (`completed_ < sequence < next_sequence_` because `completed_ < next_sequence_` and `completed_ <= sequence - 1` for the just-reserved `sequence`), so `commit_failure` no longer replaces the captured backend failure with a spurious `std::invalid_argument`. Under concurrent `submit`, the post-link catch may see `next_sequence_ == sequence + 2` (a later `submit` has already reserved), and the broad guard still accepts because `sequence` remains strictly inside `(completed_, next_sequence_)`. The new rollback branch in `submit` only fires when the backend's `queue_work` itself propagated the exception out (i.e. the link did not happen, or `commit_failure`/`complete` itself threw, or the failure escaped before `commit_failure`/`complete` was reachable).
- The CPU, CUDA, ROCm, and TTNN queue implementations are not modified; this task touches only the common `DeviceOps::submit` and `DeviceOps::commit_failure` boundaries. None of the four current `queue_work` callbacks invokes `complete(sequence)` inline, so observable backend behavior on the success path is unchanged.

## Requirements

- `DeviceOps::submit` performs the exhaustion check, the sequence read, and the `++next_sequence_` increment inside a single `std::lock_guard<std::mutex> lock(completion_mutex_)` critical section. After the lock is released, `queue_work(sequence)` runs without holding the lock. The function then returns `encode_token(sequence)`.
- The `std::overflow_error` for sequence exhaustion is raised inside the critical section (before the lock is released), so `queue_work` is never invoked when the sequence space is exhausted. The reservation has not yet happened at the exhaustion site, so the rollback path never observes an exhausted counter.
- If `queue_work(sequence)` propagates an exception, `submit` catches it, takes `completion_mutex_` again, and rolls the reservation back **only when** `next_sequence_ == sequence + 1 && completed_ < sequence` (i.e. no later `submit` on this queue has reserved a sequence since, and the failing `sequence` has not already been completed by an inline `complete(sequence)` call that preceded the throw). When both conditions hold, `submit` assigns `next_sequence_ = sequence` before rethrowing the original exception. When either condition does not hold, `submit` leaves `next_sequence_` unchanged and rethrows. The extra `completed_ < sequence` clause is required to preserve the completion invariant `completed_ <= next_sequence_ - 1`; without it, an inline-completing backend that subsequently throws past `complete` would corrupt the invariant and make future `wait`/`complete`/`commit_failure` calls on later sequences observe `completed_ >= next_sequence_`, which is invalid.
- The rollback exception category is the original exception's category — `submit` rethrows with `throw;`, not a wrapped or translated exception. The CUDA `cudaEventCreateWithFlags` `std::runtime_error` failure therefore still escapes as `std::runtime_error`, matching the `CHECK_THROWS_AS(queue->copy(...), std::runtime_error)` at `test/cuda/test_cuda_conformance.cpp:374-376`.
- A backend whose `queue_work(sequence)` synchronously calls `DeviceOps::complete(sequence)` observes `sequence < next_sequence_` at the moment of the inline `complete` call (because the increment has already happened under the lock, and the backend has not thrown). The `sequence >= next_sequence_` guard in `complete` at `src/iom.cpp:578-581` therefore fails closed in the correct direction: it does not throw, the failure table is updated as usual, and the caller's `wait(oid)` returns without blocking.
- `DeviceOps::commit_failure`'s new guard is exactly the conjunction `sequence < next_sequence_ && sequence > completed_`, accepting any reserved-but-not-completed sequence. Concretely, in evaluation order:
  1. `sequence == 0` → `std::invalid_argument("retained failure sequence is zero")` (unchanged).
  2. `!failure` → `std::invalid_argument("retained failure is empty")` (unchanged).
  3. `sequence >= next_sequence_` → `std::invalid_argument("retained failure is not for a reserved submission")` (updated message text; the never-submitted case).
  4. `sequence <= completed_` → `std::invalid_argument("retained failure is for a sequence that has already been completed")` (new rejection; the already-completed misuse case).
  5. Otherwise: `pending_failures_[sequence] = std::move(failure);` (unchanged).
  The post-link `commit_failure(sequence, failure)` calls at `src/cuda/copy.cu:494` and `src/rocm/copy.hip:432` see `next_sequence_ >= sequence + 1` and `completed_ < sequence` (because the catch is reached before the worker drains and completes the task) and are accepted; `pending_failures_[sequence]` is populated; the eventual worker `complete(sequence, failure)` call (which reads `pending_failures_`) stores the failure on `failures_[sequence]`, and `wait(oid)` rethrows on every call, exactly as before. Under concurrent `submit` (a later `submit` has reserved `sequence + 1` before the catch runs), the `sequence < next_sequence_` half of the guard still holds because the half-open interval `(completed_, next_sequence_)` still contains `sequence`; `commit_failure` still accepts. The already-completed rejection fires only if a misuse tries to attach a new failure to a sequence whose `Task` has already been drained through `complete()` (which would have already moved `pending_failures_[sequence]` into `failures_[sequence]`); that path is a programming error in the backend and the rejection with `std::invalid_argument` matches the existing rejection category.
- The CPU, CUDA, ROCm, and TTNN queue implementations require no change because they call `submit` from a single backend thread and their `queue_work` callbacks either stage-only (CPU/TTNN) or stage-then-launch-and-catch (CUDA/ROCm), so the rollback branch fires on the synchronous `queue_work` failure sites (`cudaEventCreateWithFlags`/`hipEventCreateWithFlags` failing under `SubmissionFault::event_create`) and the next successful `copy` returns the expected sequence number, e.g. 2 at `test/cuda/test_cuda_conformance.cpp:377-378`.
- The `test_iom.cpp` regression test file adds a dedicated inline-completing `FakeQueue` variant class (a sibling to `FakeQueue`) used only by the new regression test. The variant's `copy` override routes the queue_work callable through a helper that calls `complete(sequence)` directly before returning. The variant exposes a counter of how many times its queue_work callable has been invoked. The existing deterministic-deferred `FakeQueue` paths (`probe`, `copy`, `add`, `mul`, `silu`, `linear`, `rmsnorm`, `sdpa`) keep their current "stage, then test thread plays the worker" shape.
- The new regression test exercises the dedicated inline-completing `FakeQueue` variant through the public `DeviceOps::copy` entry point and asserts the post-fix invariants named in the Acceptance criteria.
- The exception categories remain the established repository set: `std::overflow_error` for sequence exhaustion, `std::invalid_argument` for invalid tokens / never-submitted sequences / "completion of a sequence that was never submitted" / `commit_failure` rejections, `std::runtime_error` for backend capability rejections and CUDA/HIP driver wrappers, and `std::current_exception()` retention on the retained-failure path. The fix does not introduce any new exception category; the rollback branch uses `throw;` and preserves the propagating exception verbatim. The updated `commit_failure` guard keeps the `std::invalid_argument` rejection category but updates the never-submitted message text and adds the already-completed message text as specified.
- The lock granularity change must not introduce a deadlock: `DeviceOps::submit`'s lock is released before `queue_work` runs, and `DeviceOps::complete`/`commit_failure`/`wait` take the same lock independently. A backend whose `queue_work` calls `complete` or `commit_failure` therefore acquires the lock a second time after `submit` has released it; no recursive acquisition is possible because the lock is `std::mutex`, not `std::recursive_mutex`. The rollback branch acquires the lock after `queue_work` has returned (normally via the exception unwinding), so there is no overlap with the critical section that performed the reservation. `commit_failure`'s new guard runs under the same single `std::lock_guard` pattern as today.
- The doc comment at `include/iom/iom.hpp:74-82` is updated to describe the new invariant: sequence reservation happens up front, exhaustion throws before `queue_work`, a synchronous `queue_work` exception rolls back the reservation in the single-threaded call shape only when the failing sequence has not already been completed, and an inline-completing backend may call `complete(sequence)` from inside `queue_work`. The comment must explicitly note that under concurrent `submit` calls on the same queue the rollback cannot reclaim a sequence that a later `submit` has already reserved, so the next non-failing `submit` observes a monotonic gap; and that if an inline `complete(sequence)` precedes a subsequent throw from the same `queue_work`, the rollback is suppressed so the completion invariant `completed_ <= next_sequence_ - 1` remains true.
- The doc comment at `src/iom.cpp:596-610` (or wherever `commit_failure` is documented in the implementation file) is updated to describe the new guard's accepted shape: any reserved-but-not-completed sequence (`sequence < next_sequence_ && sequence > completed_`); never-submitted (`sequence >= next_sequence_`) and already-completed (`sequence <= completed_`) sequences still throw `std::invalid_argument` with the updated messages.
- The no-consumption invariant for the synchronous failure sites listed above is preserved exactly in the single-threaded call shape used by every backend today. The CUDA conformance test at `test/cuda/test_cuda_conformance.cpp:372-379` continues to pass without modification: a `SubmissionFault::event_create` `copy` followed by a successful `copy` returns sequence 2 from the second call.

- Changing `DeviceOps::complete`, `DeviceOps::wait`, `DeviceOps::seek_next_sequence`, `DeviceOps::encode_token`, the queue-ID pool, or the sequence bit layout. In particular, the `complete` guard `sequence >= next_sequence_` stays exactly as written; the `wait` guard `sequence >= next_sequence_` stays exactly as written.
- Removing the `sequence >= next_sequence_` guard in `DeviceOps::complete`. The guard stays exactly as written; the fix changes the value `next_sequence_` takes at the moment of an inline `complete`, not the guard itself.
- Adopting `std::recursive_mutex` for `completion_mutex_`. A backend whose `queue_work` calls `complete` or `commit_failure` is expected to acquire the lock a second time after `submit` releases it; that is sequential acquisition, not recursion, and the existing `std::mutex` is sufficient.
- Promoting the retained-failure contract from spec 19 to inline-completing backends. The retained-failure contract (capture `std::current_exception()`, call `complete(sequence, failure)` (with `commit_failure` first if the task has been linked), return a valid `oid`) is preserved verbatim by the fix for the post-link branch that has already linked the task; the new rollback branch in `submit` only fires when the backend's `queue_work` propagated the exception out.
- Adding a public "cancel" operation, cross-queue dependencies, or any implicit waiting in `~DeviceOps`.
- Cross-cutting refactors of the queue scaffolding (spec 19 / 20 / 27 work is preserved verbatim; this is a narrow `submit` + `commit_failure` boundary change).
- Promoting the inline-completion shape through `add`, `mul`, `silu`, `linear`, `rmsnorm`, or `sdpa`, all of which currently reject with capability `std::runtime_error` before submission.
- Implementing an inline-completing backend. The change reserves the contract; it does not introduce such a backend. The CUDA, ROCm, CPU, and TTNN queues remain staged workers; the inline-completion shape is exercised only by the new `FakeQueue` regression variant.
- **Completion invariant preserved by rollback suppression:** the rollback condition `next_sequence_ == sequence + 1 && completed_ < sequence` ensures that the invariant `completed_ <= next_sequence_ - 1` is preserved for every `submit`'s catch branch. An unconditional rollback after an inline `complete(sequence)` followed by a subsequent throw would assign `next_sequence_ = sequence` while `completed_ == sequence`, violating the invariant and making future `wait`/`complete`/`commit_failure` calls on later sequences invalid. The fix must not introduce any code path that unconditionally assigns `next_sequence_ = sequence` from the catch branch.
