# Cover tile-aligned multi-tile-column shapes in the direct-storage oracle matrix

**Order:** 52
**Priority:** P0 — high-severity oracle coverage required to enforce the canonical storage invariant (CC-001); without these shapes the shared oracle and every backend conformance sweep are structurally blind to the canonical tile-aligned geometry
**Blocked by:** 51-CC-001-enforce-cpu-tiled-row-walk — CC-001's CPU tiled-row walk fix must land first so that `{16,32}` and `{2,3,16,48}` are correctly walked by `for_each_tile` / `for_each_tile_lockstep`; this task then asserts the layout post-fix via the oracle
**Source:** `docs/changes/0001-tensor-view/review.md` — `CC-002`
**Review severity:** high
**Review verification:** verified, confidence 93

## Outcome

`run_storage_oracle_conformance` and `run_storage_and_transfer_conformance` consume owner shapes whose last dimension is an exact multiple of 16 and spans at least two tile columns — at minimum `{16, 32}` (rank two, two tile columns, one tile row) and `{2, 3, 16, 48}` (leading rank two, three tile columns, one tile row). On every backend the new shapes force the tile column walk to execute for at least tile column index 1, so the self-cancelling fast-path defect of CC-001 (writing row data contiguously inside tile column 0 and never touching the true slot of element `(0, 16)`) becomes directly observable in `tiled_storage_nbytes()`. With CC-001 unfixed, `run_storage_oracle_conformance` over the new shapes fails on CPU; with CC-001 fixed, the same sweep passes on CPU, CUDA, ROCm, SYCL, and TTNN. NT-004 continues to own asymmetric stride, minimal-extent, and row-tail-only coverage and is not absorbed here.

## Current failure

Spec §4 (element `[..., row, column]` lives at slot `(plane*ceil(rows/16)*ceil(cols/16) + (row/16)*ceil(cols/16) + column/16)*256 + (row%16)*16 + (column%16)`) and §11.2 (CPU tests "write independently chosen encoded byte patterns into padded tensors and inspect the allocation directly … prevents a matching pair of incorrect pack/unpack functions from passing through round-trip cancellation") together require a storage oracle that physically observes the candidate's complete padded allocation.

`transfer_owner_shapes()` at `test/backend/backend_conformance_copy_storage.hpp:168-178` returns `{16, 16}, {1, 17}, {17, 33}, {4, 3, 17, 33}, {2, 3, 4, 17, 33}, {2, 2, 2, 3, 17, 33}`. `copy_owner_shapes()` at `:255-263` returns `{17, 33}, {2, 3, 16, 16}, {2, 3, 4, 17, 33}, {2, 2, 2, 3, 17, 33}`. Every shape either pads the last dimension up to the next multiple of 16 (so the per-tile-column loop runs once for tile column 0 only) or has exactly one tile column in the last dimension (`{16, 16}`, `{2, 3, 16, 16}` — the aligned fast path degenerates to a correct 16-element run because `columns / 16 == 1`). No shape has `columns ∈ {32, 48, 64, …}`. CC-001 (CPU `for_each_tile` / `for_each_tile_lockstep` row-strip fast path in `src/cpu/device.cpp:239-242, 351-357`, materialized by `copy_tile_row_byte_aligned` `:99-106` and `copy_tile_row_subbyte` `:128-134`, consumed by `region_from_host` `:594-642`, `region_to_host` `:682-727`, and `CpuQueue::copy_elements` `:910-952`) writes row `0`'s elements contiguously inside tile column 0 only and never reaches the spec slot of element `(0, 16)`. The shared oracle compares full native storage against `encode_standard_tiled_storage` (built from `iom::detail::standard_layout_slot` at `include/iom/tensor.hpp:119`) and would have caught CC-001 had an aligned multi-tile-column shape been present; with the existing matrix it cannot. CPU-local physical-layout cases in `test/cpu/test_cpu.cpp` use columns ∈ {1,3,5,7,11,13,16,17,33} only — same blind spot by a different mechanism.

## Scope

- Add unpadded, tile-aligned multi-tile-column owner shapes to the shared conformance matrix, at minimum `{16, 32}` and `{2, 3, 16, 48}`; the shapes are introduced into both `transfer_owner_shapes()` and `copy_owner_shapes()` so every cross-checking sweep that consumes the matrix exercises them.
- `storage_oracle_owner_shapes()` (`:297-306`) is already the union of the two lists and inherits both new shapes with no further code change.
- Each new shape must be tile-aligned on the last dimension (multiple of `TensorSpec::TILE`) and must span `>= 2` tile columns in the last dimension so that the per-tile-column walk performs at least one iteration past index 0.
- Each new shape is added exactly once to `transfer_owner_shapes()` and exactly once to `copy_owner_shapes()`. `storage_oracle_owner_shapes()` (`:297-306`) deduplicates entries that already appear in both lists, so each new shape ends up as exactly one entry in the union. Do not place a shape into one list only and rely on the union to lift it everywhere: the host-transfer sweep, the copy sweep, and the oracle sweep each consume their own list, and only the oracle consumes the union.
- The existing oracle machinery (`run_storage_oracle_conformance`, `AcceleratorStorageOracle`, `encode_standard_tiled_storage` in `test/backend/backend_conformance_oracle.hpp`) is reused unmodified; this task adds data, not infrastructure.
- The reshape / stride / extension gaps named in NT-004 (differing plane-stride pairs, `{1, 1}` minimal extent, `{17, 16}` row-tail only) are not in scope and remain owned by NT-004.
- `view_cases_for` (`test/backend/backend_conformance_copy_storage.hpp:46-166`) and `copy_cases_for` (`:193-253`) are not changed; the existing case builders already emit sensible cases on the new shapes (`{2, 3, 16, 48}` exercises every leading permutation and stepped slice path; `{16, 32}` exercises the rank-two suite unchanged).
- Pre-fix validation behavior: `run_storage_oracle_conformance` must fail on CPU at the first divergent byte inside the padded 16x16 tile at `(0, 16)` for `{16, 32}` (slot 256 for one byte starting at byte `256 * element_bytes`). Post-fix: the same sweep passes on CPU, CUDA, ROCm, SYCL, and TTNN with no oracle-side code change.

## Requirements

- The added shapes must be exact multiples of `TensorSpec::TILE` on the last dimension and must produce a standard-padded shape equal to themselves (`[16, 32]` and `[2, 3, 16, 48]` are already tile-aligned; no rounding applies).
- The added shapes must span `>= 2` tile columns in the last dimension so the per-tile-column loop performs at least one iteration past index 0; both `{16, 32}` (two tile columns) and `{2, 3, 16, 48}` (three tile columns) satisfy this. Do not add shapes whose last dimension is a single tile column; those already exist and do not exercise the loop boundary.
- `storage_oracle_owner_shapes()` must include both new shapes exactly once each (it deduplicates entries from `transfer_owner_shapes()` and `copy_owner_shapes()`); the unique-by-set semantics in `:297-306` handle this without code change.
- Pre-CC-001-fix evidence: running `iom_backend_conformance_cpu_tests` with the new shapes must produce a `REQUIRE_MESSAGE` failure from `require_storage_oracle_bytes` at byte `256 * element_bytes` for `{16, 32}` (the byte of element `(0, 16)` in the standard layout) or at the corresponding first-divergent slot for `{2, 3, 16, 48}`. The CPU reference allocation in `src/cpu/device.cpp` writes element `(0, 16)` to byte 64 (slot 16) instead of byte 1024 (slot 256) under the bug; CC-001's storage observes the spec position and demands byte `256 * element_bytes`.
- Post-CC-001-fix behavior: every shape in the matrix — including the two new entries — passes `run_storage_oracle_conformance`, `run_storage_and_transfer_conformance`, and `run_async_copy_conformance` on every backend enabled in the build.
- The shapes must round-trip via the existing `view_cases_for({16, 32})` and `view_cases_for({2, 3, 16, 48})` paths without per-shape branches. The case builder already returns a `"full"` view plus the matching slice/select/permute/reshape cases for each rank; the new shapes require no case-builder change.
- Each driver's conformance sweep over the new shapes must complete with zero `TrafficGate` allocator calls inside transfers, exactly as the existing shapes do.
- The two new shapes must appear in both `transfer_owner_shapes()` and `copy_owner_shapes()` so that host-transfer (`run_storage_and_transfer_conformance`), copy (`run_async_copy_conformance`), and oracle (`run_storage_oracle_conformance`) sweeps each observe the canonical tile-aligned geometry. The deduplication in `storage_oracle_owner_shapes()` (`:297-306`) collapses the two literal entries into one union entry, so the oracle runs each new shape exactly once even though it is listed twice.
