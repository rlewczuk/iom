# Expose one `Device::supported_data_types()` predicate and migrate every conformance driver to it

**Order:** 31
**Priority:** P0 — public-contract capability surface: every accelerator factory and the CPU reference advertise the same backend-neutral query; per-driver leaf lists stop drifting from the implementation; reject-before-allocation and fail-don't-skip semantics are preserved verbatim.
**Blocked by:** None
**Source:** `docs/changes/0001-tensor-view/review.md` — `AR-003`
**Review severity:** medium
**Review verification:** verified, confidence 85

## Outcome

`iom::Device` (`include/iom/device.hpp`) gains exactly one pure-virtual capability method, `[[nodiscard]] virtual std::span<const iom::DataType> supported_data_types() const noexcept = 0;`, declared between the existing `backend_kind()` and `backend_device()` accessors. Each of the five concrete production backends overrides it exactly once, returning a span whose contents are byte-identical to today's per-backend membership:

- `CpuDevice::supported_data_types()` returns a span over a file-local `constexpr std::array kCpuSupportedDataTypes` with 23 entries in the same order as the existing `kCpuLeafTypes` at `test/cpu/test_cpu_conformance.cpp:21-34` (BOOL, I2, U2, I4, U4, I8, U8, I16, U16, I32, U32, I64, U64, F4_E2M1, F6_E2M3, F6_E3M2, F8_E4M3FN, F8_E5M2, F8_E8M0, F16, BF16, F32, F64).
- `SyclDevice::supported_data_types()` returns a span over a file-local `constexpr std::array kSyclSupportedDataTypes` with the same 23 entries in the same order as the existing `kSyclLeafTypes` at `test/sycl/test_sycl_conformance.cpp:26-40`.
- `CudaDevice::supported_data_types()` returns a span over a file-local `constexpr std::array kCudaSupportedDataTypes` with the same 23 entries in the same order as the existing `kCudaLeafTypes` at `test/cuda/test_cuda_conformance.cpp:28-42`.
- `RocmDevice::supported_data_types()` returns a span over a file-local `constexpr std::array kRocmSupportedDataTypes` with the same 23 entries in the same order as the existing `kRocmLeafTypes` at `test/rocm/test_rocm_conformance.cpp:29-43`.
- `TtnnDevice::supported_data_types()` returns `iom::ttnn_supported_data_types()` (the nine-entry `std::span<const iom::DataType>` already exposed at `include/iom/ttnn/device.hpp:19`, `src/ttnn/device.cpp:437-439`, with the nine entries BOOL, U8, I8, U16, I16, U32, I32, BF16, F32 from `kSupportedDataTypes` at `src/ttnn/device.cpp:37-47`). The override is a single forward; no parallel table.

The four hardcoded driver lists `kCpuLeafTypes`, `kCudaLeafTypes`, `kRocmLeafTypes`, `kSyclLeafTypes` are deleted. Every conformance `TEST_CASE` that previously took one of those constants now feeds the shared scenarios from `device->supported_data_types()` on the candidate device under test. The capability query is read-only and has no side effects on `create_tensor`.

## Current failure

The review found that capability modeling is asymmetric in three ways:

1. **TTNN exposes a free function, every other backend exposes nothing.** `iom::ttnn_supported_data_types()` (`include/iom/ttnn/device.hpp:13-19`, `src/ttnn/device.cpp:437-439`) returns a `std::span<const iom::DataType>` over the file-local `constexpr std::array kSupportedDataTypes` (nine entries: BOOL, U8, I8, U16, I16, U32, I32, BF16, F32 — `src/ttnn/device.cpp:37-47`). CPU/CUDA/ROCm/SYCL expose no such surface; their supported leaf set is observable only by constructing a tensor and inspecting whether the constructor throws. The TTNN free function is the only backend-namespaced capability query in the public API, so every other backend's capability is invisible until allocation.

2. **Four hardcoded conformance driver lists duplicate that membership.** `test/cpu/test_cpu_conformance.cpp:21-34` (`kCpuLeafTypes`, 23 entries), `test/cuda/test_cuda_conformance.cpp:28-42` (`kCudaLeafTypes`, 23 entries), `test/rocm/test_rocm_conformance.cpp:29-43` (`kRocmLeafTypes`, 23 entries), and `test/sycl/test_sycl_conformance.cpp:26-40` (`kSyclLeafTypes`, 23 entries) each list every leaf type the harness is expected to exercise. The four lists are byte-identical to each other (BOOL, I2/U2, I4/U4, I8/U8, I16/U16, I32/U32, I64/U64, F4_E2M1, F6_E2M3, F6_E3M2, F8_E4M3FN, F8_E5M2, F8_E8M0, F16, BF16, F32, F64 — 23 entries) and are passed to the eight shared scenarios (`run_storage_and_transfer_conformance`, `run_storage_oracle_conformance`, `run_async_copy_conformance`, `run_copy_error_conformance`, `run_transfer_error_conformance`, `run_lifetime_conformance`, `run_compute_capability_conformance`, `run_backend_conformance`).

3. **Two parallel capability statements on TTNN.** The TTNN backend carries two capability statements today: the `kSupportedDataTypes` array (`src/ttnn/device.cpp:37-47`) and the `is_supported` linear scan over it (`src/ttnn/device.cpp:49-54`). The `native_dtype` switch (`src/ttnn/device.cpp:57-72`) enumerates the same set a third time as part of the same TU. AR-003 does not collapse any of these statements; it only routes the `Device`-level query through the existing `iom::ttnn_supported_data_types()` free function.

A driver list drifting from the implementation silently tests the wrong capability set. Adding a new leaf type or backend requires editing the backend plus every per-driver list, and drift fails nowhere until hardware runs.

- Modifying `iom::Device::backend_kind`, `iom::Device::backend_device`, the `Tensor` / `TensorView` / `TensorSpec` types, `iom::Allocator`, or any `DeviceOps` member. The new method is additive on the device contract; nothing else moves.

- Resolving the test-side `native_dtype` oracle duplication. That is a separate follow-up outside AR-003's scope.
