# Store `TensorView` by value in CPU and TTNN queue tasks instead of raw `TensorView*` to caller-owned temporaries

**Order:** 48
**Priority:** P0 — high-severity lifetime/safety defect: every caller passing a derived `TensorView` (slice/select/permute/reshape_leading) to `CpuQueue::copy` / `TtnnQueue::copy` without binding to a named local is undefined behavior today; the minimal fix is one value-copied `TensorView` per task, copy-constructed at submission time on the caller thread, so the worker never dereferences a stack temporary.
**Blocked by:** `30-AR-002-share-backend-queue-scaffold`
**Source:** `docs/changes/0001-tensor-view/review.md` — `ST-002`
**Review severity:** high
**Review verification:** strongly-supported, confidence 92

## Outcome

`CpuQueue::copy` and `TtnnQueue::copy` no longer store the addresses of their `TensorView` parameters in the queued `Task`. Each `Task` carries the `TensorView` by value, copy-constructed at submission time: a `TensorView` has a default copy constructor (`include/iom/tensor.hpp:149`) and a copy captures the exact view metadata — `TensorSpec spec_`, `std::size_t plane_offset_`, `std::vector<std::size_t> plane_strides_`, and the `Tensor* owner_` pointer — so the queued task owns the same logical view the caller passed. The worker reads the value-copied `TensorView` directly; no pointer to the caller's stack frame is ever stored. The TTNN queue no longer caches raw `const ttnn::Tensor*` / `ttnn::Tensor*` derived from `native_handle()` into the `Task`; the worker derives the native plane pair from the still-live copied view's `Tensor*` owner on each call. `Tensor` ownership stays `std::unique_ptr` throughout — no `std::shared_ptr`, no `enable_shared_from_this`, no `Device::create_tensor` API change. Caller code that does `queue->copy(t->view().slice(0,0,1), u->view().slice(0,0,1))` is no longer undefined behavior; the temporary is copy-constructed into the `Task` value before the call returns.

## Current failure

`CpuQueue::copy` (`src/cpu/device.cpp:268-291`) stores `&source` and `&destination` directly into `Task::source` / `Task::destination`:

```text
staged_.push_back(
        Task{sequence, &source, &destination,
             identical_window});
```

`source` and `destination` are references to the `TensorView` parameters of `copy`. `copy` returns by the time the worker dereferences either pointer. Today the only reason the existing call sites work is that the conformance harness binds the derived view to a named local (`test/backend/backend_conformance_copy_storage.hpp:528-535`):

```text
iom::TensorView candidate_source_view =
        copy_case.build_source(candidate_source->view());
iom::TensorView candidate_destination_view =
        copy_case.build_destination(candidate_destination->view());
...
candidate_queue->copy(candidate_source_view, candidate_destination_view);
```

Any caller that writes the natural usage `queue->copy(t->view().slice(0,0,1), u->view().slice(0,0,1))` constructs a temporary `TensorView` per argument, stores its address, and lets the temporary die at the semicolon. The worker then dereferences a dangling pointer. The hazard is silent on the current suite because the harness never reaches the temporary path.

`TtnnQueue::copy` (`src/ttnn/device.cpp:283-295`) adds a second hazard: it also stores `static_cast<const ttnn::Tensor*>(source.native_handle())` and `static_cast<ttnn::Tensor*>(destination.native_handle())` as raw pointers into `Task::source_planes` / `Task::destination_planes`. These point into the owning `TtnnTensor::planes_` `std::vector<ttnn::Tensor>` (`src/ttnn/device.cpp:212`). The native-handle caching is a separate concern from the temporary-view hazard: the cached pointer is derived from the `TensorView`, and once the value-copied `TensorView` lives inside the `Task`, the worker derives the native handle on demand through the view's owner rather than caching it at submission time. Owner destruction while queued is a separate lifetime concern handled by ST-003 (`49-ST-003-fence-backend-queue-teardown`); ST-002 only fixes the temporary-view hazard by ensuring no caller-stack pointer is stored.

The review's invariant ("A queued async operation may only reference resources that outlive every queued operation — derived `TensorView`s from `slice`/`select`/`permute`/`reshape_leading` are temporaries.") and failure mode (`Task` stores the addresses of the `copy(const TensorView&, TensorView&)` parameters; the natural usage pattern leaves the worker dereferencing stack temporaries whose lifetime ended at the semicolon) are the remediation target. The minimal fix collapses the hazard by copy-constructing the view into the task at submission time; the worker then reads only the value-copied view.

## Scope

- Replace the `const TensorView* source` and `TensorView* destination` fields of `CpuTask` with two `TensorView` value members. `TensorView` has only a default copy constructor and a default move constructor (`include/iom/tensor.hpp:149-150`); both copy and move assignment are explicitly `= delete` (`include/iom/tensor.hpp:151-152`). The view value members MUST therefore be initialized at construction (member-initializer-list or constructor argument), not assigned later. Add a `Task` constructor that takes `(std::uint64_t sequence, const TensorView& source, TensorView& destination, bool no_op)` and member-initializes `source(source)`, `destination(destination)`. Aggregate initialization is impossible because `TensorView` has no default constructor (only the private `Tensor`-friend constructor exists, `include/iom/tensor.hpp:178-179`).
- Replace the `const TensorView* source` / `TensorView* destination` / `const ttnn::Tensor* source_planes` / `ttnn::Tensor* destination_planes` fields of `TtnnTask` with two `TensorView` value members. Remove the cached `ttnn::Tensor*` fields entirely; the worker derives native handles from the copied `TensorView`'s owner per call. `TtnnTask` gains a constructor with the same shape as `CpuTask`'s.
- Adjust `CpuQueue::execute` (the helper's `Callbacks::execute`, post-AR-002) and `TtnnQueue::execute` to consume `task.source` and `task.destination` as `const TensorView&` / `TensorView&` value references. The `copy_elements` and `ttnn_detail::copy_planes` calls take the value-copied views directly; no pointer indirection through a stored `TensorView*`.
- For the TTNN worker, derive `source_planes` and `destination_planes` from the value-copied `TensorView` at execution time. Two acceptable shapes: (a) keep the existing `ttnn_detail::copy_planes(const TensorView&, const ttnn::Tensor*, const TensorView&, ttnn::Tensor*)` signature and pass `static_cast<const ttnn::Tensor*>(task.source.native_handle())` plus the destination equivalent on the worker thread; (b) introduce a private static helper `ttnn_detail::planes_pair(const TensorView&)` that returns `std::pair<const ttnn::Tensor*, ttnn::Tensor*>` derived from the view's owner's `TtnnTensor` cast. Both shapes avoid caching the pointer in the `Task` itself; the pointer is computed once per execution.
- Preserve the AR-002 `StagedWorker<Task>` helper shape exactly: `Task` gains only the AR-002 field `void* fence = nullptr` (the lifetime fence pointer for CUDA/ROCm; CPU/TTNN keep `fence` as `nullptr`). The four callbacks `Callbacks::execute`, `Callbacks::fence_complete`, `Callbacks::fence_destroy`, `Callbacks::complete` and the `PublishPolicy::Splice` (CUDA/ROCm) / `PublishPolicy::CompleteOnThrow` (CPU/TTNN) distinction from AR-002 are preserved verbatim. **ST-002 does not add a per-task `std::exception_ptr failure` field**; that field is the ST-006 retained-failure contract owned by `27-ST-006-bound-rocm-failure-wait` and `19-ST-002-transactional-cuda-rocm-submission` / `30-AR-002-share-backend-queue-scaffold`, not by this finding. The pre-existing AR-002 `Task` shape is preserved exactly; only the two view-storage fields change.
- Preserve the existing sequence-before-queue-work, no-destruction-wait, commit-before-complete, identical-window no-op, validation-before-sequence, and `validate_copy` exception contracts untouched. `DeviceOps::copy` (`include/iom/iom.hpp:46`) stays pure virtual; its public override contract is unchanged.
- Preserve the public `DeviceOps::wait` / `DeviceOps::complete` / `DeviceOps::submit` surface untouched. The change is internal to the `CpuQueue` and `TtnnQueue` translation units and the `TensorView` copy-construction path.
- Preserve the `Tensor` ownership model: every `Tensor` is owned by exactly one `std::unique_ptr<Tensor>` (`include/iom/tensor.hpp:201-206`, `src/cpu/device.cpp:445-447`, the device create_tensor factories). No `std::shared_ptr` is introduced. The `TensorView::owner_` pointer stored inside the value-copied view continues to be a non-owning raw pointer to the same `Tensor` the caller passed; ST-003 (`49-ST-003-fence-backend-queue-teardown`) handles the case where the owner is destroyed while the task is queued, and that case is out of scope here.

## Requirements

- **Constructor-based Task initialization:** every queued `CpuTask` and `TtnnTask` is constructed with the new `Task(std::uint64_t sequence, const TensorView& source, TensorView& destination, bool no_op)` constructor. The constructor member-initializes `source(source_)` and `destination(destination_)` from the caller-thread `TensorView` references. No assignment is performed on `task.source` or `task.destination` after construction; both view members are immutable from the caller's perspective for the task's lifetime. The `void* fence = nullptr` field is a default member initializer and is never assigned at the call site.
- **No `TensorView::operator=` calls in any Task path:** because both `TensorView::operator=(const TensorView&)` and `TensorView::operator=(TensorView&&)` are `= delete` (`include/iom/tensor.hpp:151-152`), the queued `Task` cannot ever be assigned a view; the only legal path is constructor member-initialization. `grep -nE 'task\.(source|destination)\s*=' src/cpu/device.cpp src/ttnn/device.cpp` returns zero matches post-fix. `grep -nE 'TensorView&\s+operator=' src/cpu/device.cpp src/ttnn/device.cpp` returns zero matches.
- **Value-copied view:** every queued `CpuTask` carries `TensorView source` and `TensorView destination` by value. Every queued `TtnnTask` carries the same. No raw `TensorView*` or `ttnn::Tensor*` appears in any `Task` struct after this change. `grep -E 'TensorView\*\s+(source|destination)|ttnn::Tensor\*\s+(source|destination|source_planes|destination_planes)' src/cpu/device.cpp src/ttnn/device.cpp` returns no matches in any `Task` field declaration post-fix.
- **AR-002 task shape preserved:** the `Task` struct gains only `void* fence = nullptr` (matching the AR-002 contract for CUDA/ROCm fence shape parity). **No `std::exception_ptr failure` field is added by ST-002.** The retained-failure contract is owned by `27-ST-006-bound-rocm-failure-wait` and `19-ST-002-transactional-cuda-rocm-submission` / `30-AR-002-share-backend-queue-scaffold`, which are not in scope here. `grep -n 'failure' src/cpu/device.cpp src/ttnn/device.cpp` returns no new matches in any `Task` field declaration post-fix beyond whatever AR-002 itself introduces.
- **AR-002 worker extraction must move-construct, not assign:** the post-AR-002 `iom::detail::StagedWorker<Task>::run()` step 4 extracts the front of `tasks_` into a local `Task current`. Because both `TensorView::operator=(const TensorView&)` and `TensorView::operator=(TensorView&&)` are `= delete` (`include/iom/tensor.hpp:151-152`), and `Task` aggregates those view members, the extraction cannot use `Task current; current = std::move(tasks_.front());` (default-construct then move-assign). It cannot use `current = std::move(tasks_.front());` either (move-assign without prior default). The ONLY legal shape is move-construction: `Task current(std::move(tasks_.front())); tasks_.pop_front();`. `Task` must have a defaulted or user-provided move constructor (the defaulted one is sufficient because every member is move-constructible: scalars, `TensorView` default move ctor, `std::vector<std::size_t>` move ctor — `void*` is trivially move-constructible). The helper's `run()` body MUST be updated to use this move-construction shape; any prior `Task current = default; current = std::move(...);` or `Task current{}; current = ...` shape is illegal under ST-002's `Task` contract. The same move-construction shape applies to `shutdown_and_drain()` step 4 (`Task entry(std::move(staged_.front())); staged_.pop_front();` followed by `fence_destroy`/`complete`). `grep -nE 'Task\s+current\s*[;=]|current\s*=\s*std::move\(tasks_' include/iom/iom.hpp src/cpu/device.cpp src/ttnn/device.cpp` returns zero matches with assignment operators; the only legal pattern is `Task current(std::move(tasks_.front()));`.
- **TensorView copy construction semantics:** the queued `Task`'s view copies are constructed at submission time, on the caller thread, inside the `submit` lambda body **as arguments to the `Task` constructor** before `worker_.submit_copy(std::move(task))` runs. The two copy constructors capture `source.spec_`, `source.plane_offset_`, `source.plane_strides_`, and `source.owner_` (and the destination equivalents) into the `Task`'s value members before the `submit` lambda returns. The worker reads the copy-constructed view's members; no pointer to the caller's stack `TensorView` is ever stored.
- **TTNN native handle derived on the worker:** the TTNN `Task` does not cache `const ttnn::Tensor*` or `ttnn::Tensor*`. The worker derives the native handle from `task.source.native_handle()` and `task.destination.native_handle()` at execution time (cast to `ttnn::Tensor*`/`const ttnn::Tensor*` on the worker thread) and uses it for the duration of one `ttnn_detail::copy_planes` call. The pointer is a stack local; it is never copied into the `Task`.
- **TensorView lifetime contract preserved:** the value-copied view's `owner_` is a non-owning pointer to the `Tensor` the caller passed. The owner's lifetime is governed by the existing `unique_ptr<Tensor>` API and the established "owner outlives queued operations" contract (`AGENTS.md`). The value-copy makes the worker independent of the caller's stack frame; ST-003 (`49-ST-003-fence-backend-queue-teardown`) is the separate finding that enforces the owner-outlives-queued-work invariant for cases where the caller destroys the owner before `wait(token)` returns. **ST-002 does not assert, require, or test any guarantee about owner destruction while a task is queued.** This finding is strictly the temporary-view defect.
- **Identical-window no-op:** the existing `task.no_op` short-circuit is preserved. The check runs on the caller thread inside `copy` against the parameter `TensorView` references before the `Task` constructor is invoked: `source.native_handle() == destination.native_handle() && source.plane_offset() == destination.plane_offset() && std::equal(source.plane_strides().begin(), source.plane_strides().end(), destination.plane_strides().begin(), destination.plane_strides().end())`. The boolean is passed as the fourth constructor argument. When `task.no_op` is true the worker short-circuits to `complete(task.sequence, nullptr)` without invoking `copy_elements` / `ttnn_detail::copy_planes`.
- **Sequence ordering:** the value-copied views are constructed inside the `submit` lambda on the caller thread, captured by value into the `Task`, and read by the worker after `publish_staged` moves the entry to `tasks_`. No additional synchronization is required; the existing `mutex_` and `completion_` primitives inside the `StagedWorker<Task>` helper (post-AR-002) cover the lifetime.
- **Move semantics and allocation footprint:** the `Task` move operations stay default. The `TensorView` value members move cheaply (three scalars, a `std::vector<std::size_t>` heap swap, and a pointer). The `Task` is built with `Task task(sequence, source, destination, identical_window);` inside the `submit` lambda, after which `worker_.submit_copy(std::move(task));` moves the constructed `Task` into the helper's `staged_` list under `mutex_`. The only allocation the view copies introduce is the existing `std::vector<std::size_t>` copy inside `TensorView`'s default copy constructor (`include/iom/tensor.hpp:149`); no new native-resource allocation (CUDA event, ROCm event, TTNN tensor, allocator block) is introduced on the hot path.
- **TensorView copy may throw `std::bad_alloc` — propagation through `submit` / ST-007:** the `TensorView` default copy constructor can throw `std::bad_alloc` from the `std::vector<std::size_t>` copy. The view-copy construction runs **inside the `Task` constructor invocation, which itself runs inside the `submit` lambda body, before `worker_.submit_copy(std::move(task))` and before the AR-002 worker link**. Concretely, the `submit` lambda executes `Task task(sequence, source, destination, identical_window);` (which copy-constructs both `source(source_)` and `destination(destination_)` members) and then calls `worker_.submit_copy(std::move(task));`. If either view-copy throws inside the `Task` constructor, the `submit` lambda propagates the exception out of `DeviceOps::submit` before `submit_copy` is reached. Per `28-ST-007-commit-sequence-before-queue-work`, `DeviceOps::submit` reserves and increments `next_sequence_` (committing the reservation) **before** invoking the user lambda; when the user lambda throws, `submit` catches the exception and rolls the reservation back when both `next_sequence_ == sequence + 1` and `completed_ < sequence`. Concretely for ST-002: the user lambda threw before `worker_.submit_copy(std::move(task))` was reached, so no `Task` was linked into `staged_`, no worker work exists, no native resource was allocated, no destination was modified, and the reservation-rollback predicate holds (no later submission has reserved a sequence since, and no inline `complete(sequence)` ran). `submit` rolls the reservation back, rethrows the original `std::bad_alloc` to the caller, and returns no token. The next successful `copy` returns the same sequence number that would have been returned had the failed call never happened; no sequence is left dangling, no `wait(oid)` is ever required, and no worker observes a half-built `Task`. Exception categories are unchanged: `std::bad_alloc` from the vector copy is the established `std::bad_alloc` category (matching `LinearAllocator`/CUDA/HIP exhaustion paths). For TTNN, the `TtnnQueue::copy` path adds the same propagation; the `ttnn::Tensor*` casts inside `TtnnQueue::execute` run on the worker, never at submission time, so they cannot contribute a pre-link throw from ST-002's value-copy path.
- **Exception categories:** the existing categories are preserved verbatim. `validate_copy` throws `std::invalid_argument`; `unsupported(...)` throws `std::runtime_error`; `DeviceOps::submit`'s `std::overflow_error` exhaustion guard is unchanged; the retained-failure branch (from `19-ST-002-transactional-cuda-rocm-submission` / `30-AR-002-share-backend-queue-scaffold`) is unchanged and not extended by this finding. The `TensorView` copy constructor can throw `std::bad_alloc` as documented above. No new exception categories are introduced.
- **Backend parity:** the CPU and TTNN `Task` structs both carry `TensorView source` and `TensorView destination` value members plus the AR-002 `void* fence = nullptr` field, and both expose the same constructor signature. The TTNN `Task` is a strict subset-plus of the CPU shape; the difference is only that `TtnnQueue::execute` derives a `ttnn::Tensor*` cast on the worker thread, which `CpuQueue::execute` does not.
- **No public API drift:** `Device::create_tensor` still returns `std::unique_ptr<Tensor>`; `Tensor` still inherits nothing more than today; no `enable_shared_from_this`, no `std::shared_ptr<Tensor>`, no `plane_handle` accessor, no public method added to `TtnnTensor`. The change is entirely internal to `CpuQueue`, `TtnnQueue`, and the copy-construction path of `TensorView`.
- **Owner-destruction-while-queued:** the scope of this finding is the temporary-view hazard only. Owner-destruction-while-queued (caller destroys the `unique_ptr<Tensor>` before `wait(token)` returns) is the ST-003 finding and is enforced by the registry/fence mechanism specified in `49-ST-003-fence-backend-queue-teardown`. ST-002 does not add owner-destruction tests; ST-003 owns that regression coverage.

## Non-goals

- Adding a `std::shared_ptr<Tensor>` factory on `Device::create_tensor`. The public API stays `std::unique_ptr<Tensor>`. The TensorView value-copy in the `Task` is sufficient for the temporary-view defect; owner-shared ownership belongs to ST-003.
- Adding `std::enable_shared_from_this` to `Tensor`. The class hierarchy stays as today.
- Adding a public `TtnnTensor::plane_handle` accessor. The worker derives the native handle inline; no public surface changes.
- Adding a `std::exception_ptr failure` field to `CpuTask` or `TtnnTask`. The retained-failure contract is owned by `27-ST-006-bound-rocm-failure-wait` and AR-002. ST-002 only changes the view-storage fields; the `Task` shape otherwise matches AR-002 verbatim.
- Replacing the `ttnn_detail::copy_planes` function signature. The existing signature stays; only the call site (worker instead of caller) moves.
- Removing the `validate_copy` / `identical_window` / `unsupported` duplication that AR-002 addresses. AR-002 is the blocker; once it lands, the CPU/TTNN `copy` overrides call `DeviceOps::validate_copy` and `DeviceOps::identical_window` directly.
- Changing the public `TensorView` surface (`include/iom/tensor.hpp:147-190`). The class keeps its default copy/move constructors and deleted assignment operators; the value-copied view is what captures the view metadata.
- Adding a `cancel` operation, cross-queue dependencies, or any API change. The change is contained to CPU and TTNN `Task` types, their constructors, and the worker entry points.
- Speculative cleanup of CUDA / ROCm `Task` structs. CUDA and ROCm keep their current shape (their `submit` callback already captures the `TensorView*` addresses on the caller thread; the lifetime-fence event chain handles the CUDA/ROCm case differently). The CUDA/ROCm hazard is not in scope for ST-002.
