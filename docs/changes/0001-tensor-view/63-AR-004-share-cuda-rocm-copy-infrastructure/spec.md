# Share the CUDA/ROCm copy pools, metadata machinery, and grid-stride kernel behind the existing policy seam

**Order:** 63
**Priority:** P1 — remove synchronized CUDA/ROCm infrastructure twins after teardown fencing is restored; required consolidation that gates no correctness work
**Blocked by:** `56-ST-002-restore-gpu-event-fencing`
**Source:** `docs/changes/0001-tensor-view/review.md` — `AR-004`
**Review severity:** medium
**Review verification:** verified, confidence 90

## Outcome

The CUDA/ROCm copy infrastructure exists once. The queued-copy metadata header, its checked layout arithmetic, the host writer, the grid-stride kernel, and its launcher live in `src/shared/standard_tiled_copy.inl` behind the existing `IOM_GPU_*`/`IOM_LAUNCH_KERNEL` macros, and the staging-slot, transfer-stream, and metadata-slot pools become policy-parameterized class templates under `src/shared/`, instantiated on each backend's `gpu_policy`. `src/cuda/copy.cu`, `src/rocm/copy.hip`, and the per-backend `staging_pool`/`transfer_pool` files shrink to the genuinely divergent parts — adapter policy, fault seams, fence callbacks, and the queue classes — so the next copy-path fix is a single edit again. Observable behavior on both backends is unchanged: identical error categories and message texts, identical pool/fence semantics, identical kernel bodies and launch geometry, and unchanged conformance, fault-injection, and teardown suites on hardware.

## Current failure

Invariant (review AR-004): duplicated responsibility is consolidated behind the existing policy seam; genuinely divergent units stay per-backend.

The copy infrastructure is still policy-mirrored twins — approximately 695 identical lines across the copy translation units and pool file pairs, with zero semantic divergence:

1. Queued-copy metadata machinery, `src/cuda/copy.cu` vs `src/rocm/copy.hip`: the checked-arithmetic helpers `checked_metadata_mul`/`checked_metadata_add`/`metadata_u64`/`padded_dimension` (`:378-409` vs `:384-413`), `CudaCopyMetadataHeader`/`HipCopyMetadataHeader` (`:226-237` vs `:308-319`), `CudaMetadataLayout`/`HipMetadataLayout` + `metadata_layout` (`:411-465` vs `:415-469`), and `write_cuda_metadata`/`write_hip_metadata` (`:562-598` vs `:566-602`) are byte-identical modulo the type prefix.
2. `grid_stride_copy_kernel` (`:242-288` vs `:325-371`): identical device bodies; only the launch site differs (CUDA triple-chevron at `copy.cu:776` vs `hipLaunchKernelGGL` at `copy.hip:779`).
3. `CudaMetadataSlotPool`/`HipMetadataSlotPool` (`:467-560` vs `:471-564`): identical acquire/release/`ensure_slot_capacity`/destructor logic over the `activate`/`allocate`/`free_noexcept`/`synchronize_stream` policy calls.
4. `TransferStreamPool`: `src/cuda/transfer_pool.hpp` and `src/rocm/transfer_pool.hpp` declare the same class, and the member bodies in `copy.cu:298-375` and `copy.hip:223-296` differ only in the runtime prefix and the two closing-error strings.
5. `StagingSlotPool`: `src/{cuda,rocm}/staging_pool.hpp` and `.cpp` are identical apart from `CUdeviceptr` vs `hipDeviceptr_t`, the per-API error helper, and the backend label in the closing messages.
6. Fence resources and callbacks (`CudaFenceResource`/`cuda_fence_complete`/`cuda_fence_destroy` at `:600-632` vs `HipFenceResource`/`hip_fence_complete`/`hip_fence_destroy` at `:604-636`) and the `Task`/`SequenceOutcome`/`execute`/`complete_task` queue shells repeat the same shapes around the shared machinery.

This is the drift channel that already fired twice: PF-002's metadata rework regenerated the teardown path without 47-ST-001's synchronize (review ST-002, restored by `56-ST-002-restore-gpu-event-fencing`), and the prior review recorded a staging-padding divergence between the same backend pair. The real adapter differences — `CUcontext` + the injectable `driver_calls` seam versus `hipSetDevice(int)`, error-string helpers, launch syntax, and the pool closing messages — are already isolated inside `gpu_policy` and the `IOM_GPU_*` macros, so nothing blocks the extraction. Cost today: ~450–550 duplicated resource/pool/kernel/metadata lines that every reviewer re-verifies and every fix must edit twice.

## Scope

- **Shared metadata/kernel block:** move the metadata header struct, the checked-arithmetic helpers, the layout computation, the metadata writer, `grid_stride_copy_kernel`, and a new shared grid-stride launcher into `src/shared/standard_tiled_copy.inl` (namespace `iom::detail`), deleting the per-backend copies.
- **Shared pools:** create `src/shared/staging_pool.hpp`, `src/shared/transfer_pool.hpp`, and `src/shared/metadata_slot_pool.hpp` defining `iom::detail::StagingSlotPool<Policy>`, `iom::detail::TransferStreamPool<Policy>`, and `iom::detail::MetadataSlotPool<Policy>` with today's exact public surfaces, and delete `src/cuda/staging_pool.{hpp,cpp}`, `src/cuda/transfer_pool.hpp`, and the ROCm twins.
- **Policy promotion:** move `gpu_policy` out of the copy units' anonymous namespaces into `iom::cuda_detail`/`iom::rocm_detail` with inline members in `src/cuda/copy.hpp`/`src/rocm/copy.hpp`, extended with the small member set the shared pools require; declare `consume_submission_fault` in the headers (its definition stays beside the existing per-backend fault atomic).
- **Backend naming:** `src/{cuda,rocm}/copy.hpp` alias `StagingSlotPool`/`TransferStreamPool` to the policy instantiations so `src/{cuda,rocm}/device.cpp`, the `region_from_host`/`region_to_host` signatures, and both smoke tests keep compiling unchanged except for two include lines.
- **Queue classes stay backend-local:** `CudaQueue`/`RocmQueue` (including `Task`, `SequenceOutcome`, `execute`, `complete_task`, the fence resources, `cuda_fence_*`/`hip_fence_*`, `fence_event`/`make_fence`, `synchronize_and_destroy_stream`, the rejection stubs, and the fault atomics) are untouched except for the `metadata_pool_` member type, the fence resource's pool-pointer type, and the single launch statement in `execute`.
- **Affected backends:** cuda, rocm. CPU, SYCL, TTNN, and everything under `include/iom/` are untouched.
- **Behavior:** none — pure structural extraction with byte-identical messages, error categories, fault seams, pool semantics, kernel bodies, and launch geometry.

## Requirements

1. Single definition per shared unit: `CopyMetadataHeader`, `CopyMetadataLayout`, `copy_metadata_layout`, `write_copy_metadata`, `grid_stride_copy_kernel`, `launch_grid_stride_copy`, `StagingSlotPool`, `TransferStreamPool`, and `MetadataSlotPool` are defined exactly once under `src/shared/`; the backend units consume them via one `.inl` include at the existing macro-guarded positions (`src/cuda/copy.cu:238`, `src/rocm/copy.hip:320`) and the pool headers via `copy.hpp`. No `Cuda`-/`Hip`-prefixed twin of any of these remains.
2. Policy discipline: everything under `src/shared/` stays backend-neutral — only the `IOM_GPU_*`/`IOM_LAUNCH_KERNEL` macros and the `Policy`/template parameters touch runtime specifics; no CUDA or HIP runtime/driver symbol appears in `src/shared/`. This also keeps the `.inl` consumable by the post-task-60 SYCL include unchanged.
3. Preserved semantics, byte for byte: the metadata header layout and every overflow message; the kernel body including the padded-rows/columns arithmetic and the leading-coordinate stride walk; launch geometry (256 threads, `ceil(total_words / 256)` blocks capped at 65535) and the `third_plane_launch` fault point consumed immediately after the launch check; `kMetadataSlotCount = 16`, initial slot capacity 256, stream-synchronize-before-replacement growth, blocking slot `acquire`, idempotence-guarded `release`, and the activate-swallowing destructor; `kMaxStagingBytes = 8 GiB` with its `std::invalid_argument` text, `kMaxSlotCount = 16`, checked geometric growth, allocation-failure accounting restoration, poison-destroys-slot/stream behavior, `Lease`/`Scope` RAII, and `destroy()` close-out waits; the `IOM_ENABLE_TESTING` seams (`fail_next_allocation_for_testing` throwing `std::bad_alloc`; `idle_count_for_testing`/`allocation_count_for_testing` returning 0 when disabled).
4. Preserved diagnostics: the closing and failure paths keep today's exact texts and categories — `"CUDA staging pool is closing"` vs `"ROCm staging pool is closing"`, the transfer-pool closing errors (`"cudaStreamCreateWithFlags failed with cudaErrorStreamDestroyed: TransferStreamPool is closing"` vs the `hipErrorContextIsDestroyed` twin), and the per-API allocation messages (`cuMemAlloc` via `iom::check_cuda` with `cuGetErrorName`/`cuGetErrorString`; `hipMalloc` via `check_hip`/`hip_error`). The shared templates obtain them only through the policy factories, never by string-building in shared code.
5. Policy promotion is mechanical: `gpu_policy` keeps every existing member and its semantics (the fault-consuming `create_event`/`record_event`/`after_*` members, `record_event_no_fault`, `staging_address`, `activate` over `driver_calls` on CUDA and `hipSetDevice(int)` on ROCm); the fault state stays one `g_submission_fault` atomic per backend with `consume_submission_fault` as its single accessor, declared in `copy.hpp` and defined in the copy unit. No `include/iom/` public header changes.
6. The queue classes and their callbacks are not templated, shared, or restructured: 0002-eltwise will put real per-backend compute implementations in `CudaQueue`/`RocmQueue`, making the queues the legitimate divergence boundary (review AR-004). The only queue-body edits are the `metadata_pool_` type, the fence resource's pool-pointer type, and the `execute` launch statement.
7. The extraction is behavior-neutral by construction: no new mutex, thread, seam, allocation, or data copy; pool member layout, lock discipline, and condition-variable waits stay as written; device-owned pool lifetimes and the `~CudaDevice`/`~RocmDevice` teardown order (`activate` → `transfer_pool_.destroy()` → `staging_pool_.destroy()` before context/device release) are untouched.

- Pooling CUDA/ROCm events or passing small metadata as kernel arguments (review PF-004).
- Any `grid_stride_copy_kernel` optimization, specialization, or profiling (review PF-006); the kernel moves verbatim.
- Deleting dead state — the stored-but-unread staging-pool context member, `Task::{source,destination}` raw views, `SequenceOutcome::fence_succeeded`, `submission_order_mutex_` (review AR-006, which follows this task so it can clean the post-extraction layout).
- Sharing `registry_state.hpp`, the tensor-destructor protocol, or registry structure (review AR-002/AR-003).
- SYCL convergence (task `60-AR-001-converge-sycl-copy-architecture` owns `src/sycl`; its spec explicitly leaves these CUDA/ROCm units to this task) and any CPU or TTNN change.
- New tests, harness, fault seams, or behavioral changes of any kind; the existing suites are the gate.
