**Order:** 76
**Priority:** P2 — hypothesis-only performance finding whose review verification is explicitly "arithmetic counts code-certain; materiality unmeasured". The task is a measurement investigation; its completion evidence is the recorded profile numbers plus a falsification verdict or a concrete follow-up recommendation, delivered to the orchestrator/integrator via the standard task completion record (not as a file in the repository). P2 reflects that the task does not gate any correctness or lifetime work and that any follow-up remediation is a separate task.

## Outcome

On real CUDA and ROCm hardware the post-`63-AR-004`/`74-PF-004` shared `grid_stride_copy_kernel` in `src/shared/standard_tiled_copy.inl` is profiled through the queued-copy path (`DeviceOps::copy` via `CudaQueue::execute`/`RocmQueue::execute`, launched through `iom::detail::launch_grid_stride_copy<Policy>`) for two shapes — `{4096, 4096}` (rank-2, dense, tile-aligned, single plane) and `{4, 4, 1024, 1024}` (rank-4, dense, tile-aligned, 16 planes, total bytes identical to the rank-2 shape) — and for two dtypes (`I4` and `F32`), using the profiler documented for the host's installed toolchain. The profiler binary and version are recorded as installed; the actual supported launch-selection flag (and any kernel-name filter) is determined by reading the installed binary's own `--help` output (recorded in the completion evidence), and every command line written into the completion evidence is the verbatim output of that `--help` inspection — no flag is invented or substituted. The kernel symbol the profiler reports for the queued-copy launch is recorded verbatim from the profiler's own output (post-`74-PF-004` the mangled symbol may differ from `grid_stride_copy_kernel`; the recorded filter is whatever the profiler shows). The D2D control is a separate, explicit run that issues one `cudaMemcpy`/`hipMemcpy` of `tiled_storage_nbytes()` bytes via `TensorView::native_handle()` and is profiled by its own profiler invocation; the kernel selection (whatever name the tool exposes for the control's memcpy API call) is the tool's own. Logical correctness of the kernel path is verified through `TensorView::copy_to_host`. For each `(host, shape, dtype)` tuple the completion evidence records: the installed profiler binary and version, the verbatim `--help` excerpt that justifies each flag, the kernel-launch numbers (achieved logical GB/s over `tiled_storage_nbytes()` derived from the profiler's native duration counter and the bytes transferred), the D2D-control numbers (the same derivation, from the control's profiler invocation), the kernel/control ratio where valid, the profiler's documented speed-of-light/memory/scheduler interpretation of the launch, and a verdict — **FALSIFIED**, **CONFIRMED**, **INCONCLUSIVE**, or **BLOCKED-ON-TOOLING** — derived from the recorded evidence and the published interpretation, never from a pre-asserted threshold table. On CONFIRMED the completion evidence additionally states the measured bottleneck and a concrete follow-up recommendation for a separate task. The completion evidence (per-tuple numerical tables, verdict, and any follow-up recommendation) is delivered via the standard task completion record; no working-tree file is left at completion, and `_local/pf006-profile/` is removed by `remote-clean` after the completion evidence is finalized.

## Current failure

Invariant under review (PF-006, severity low, confidence 55, "no profiler available"): a pure data-movement kernel is memory-bandwidth-bound.

The CUDA/ROCm queued copy path executes one `grid_stride_copy_kernel` launch per non-no-op `DeviceOps::copy` (`src/cuda/copy.cu:776`, `src/rocm/copy.hip:780`). The kernel body is the post-`63-AR-004` shared device function in `src/shared/standard_tiled_copy.inl:140-186` (`copy_tiled_to_tiled_word`) with its helpers at `:71-96` (`plane_slot`, `physical_coordinate`) and `:98-138` (`merge_overlapping_field`). For each 32-bit destination word the kernel derives `padded_rows`/`padded_columns`/`padded_elements`/`plane_bits`/`words_per_plane` (4 divmods by `TensorSpec::TILE = 16` plus one by `bits`, the latter constant per submission), then for each covered slot calls `physical_coordinate` (which itself does divmods by `kTileSlots = 256` and `tile_columns`), then recomputes two `plane_slot(...)` values per slot (three divmods by `kTile`, one by `kTileSlots`, one by `tile_columns` per call, plus two multiply-adds), and finally merges the source fields with one `read_field_extracted` shift/mask per slot. The hypothesis PF-006 records is that for sub-byte types the cumulative cost of these runtime divmods and per-slot `plane_slot` recomputations drives SM/LDS issue-stall behavior large enough to leave copy throughput materially below the device-to-device `cudaMemcpyDtoD`/`hipMemcpyDtoD` roofline, with a plausibility range of 1.5–3× for I2/I4/F4/F6 (smaller for F32/BF16). The roofline ratio is unmeasured; coalescing and the launch geometry (`ceil(total_words/256)` blocks capped at 65535 with 256 threads per block, computed once on the host) are not in question. PF-006's own prescribed verification method names exactly this experiment: "Nsight Compute on I4 and F32 4096×4096 copies versus a `cudaMemcpyDtoD` baseline; confirm SM-issue-bound before committing the rewrite."

Two structural blockers prevent running that experiment today. First, the kernel sits in per-backend twins (`src/cuda/copy.cu:242-288`, `src/rocm/copy.hip:325-371`) beside per-backend metadata header types and per-backend event lifecycle code that pollutes the small-op regime with non-kernel noise (review PF-004). `63-AR-004-share-cuda-rocm-copy-infrastructure` moves the kernel to the shared `.inl` behind the existing `IOM_GPU_*` macros and the existing `gpu_policy` seam, and `74-PF-004-pool-gpu-copy-events` adds the pooled event ring so the kernel's own ALU profile is not dominated by `cudaEventCreateWithFlags`/`cudaEventDestroy`/`cudaMemcpyAsync` H2D metadata noise. Second, neither PF-002 nor 46-PF-006 produced a recorded Nsight Compute / `rocprof` run of the queued-copy kernel against a `cudaMemcpyDtoD`/`hipMemcpyDtoD` baseline. This task produces that run.

The control is profiled by its own profiler invocation; it is never combined with the kernel invocation in a single profiler run, so the recorded bytes-per-second derivation is unambiguous (the control's profiler-reported native duration counter over `tiled_storage_nbytes()` bytes is the control bandwidth in GB/s; the same derivation applies to the kernel invocation).

Counter names recorded in the completion evidence are the ones the installed profiler actually produces in its output; no counter is invented or substituted. If the installed profiler does not expose a section or counter the completion evidence records it as unavailable, not as zero.
- **Verdict classification (per `(host, shape, dtype)` tuple; the implementer does not choose):**
  - **CONFIRMED** requires both (i) corroborated ALU/scheduler pressure: the profiler's instruction-mix and scheduler-source sections together identify the kernel as ALU/issue-bound or issue-stall-bound rather than memory-bound on the profiled launch (the completion evidence quotes the profiler's own interpretation, not a thresholded ratio); AND (ii) materially sub-roofline bandwidth: the kernel's achieved logical GB/s divided by the D2D control's achieved logical GB/s (over `tiled_storage_nbytes()`, for the valid control) is materially below the control on at least one of `{I4, F32}` for the host. "Materially below" is recorded as the completion evidence's number, not asserted against a fixed percentage.
  - **FALSIFIED** records when the kernel is memory-bandwidth-bound (profiler speed-of-light memory section at or near the documented roofline, ALU/scheduler sections not the binding constraint) AND/OR the kernel/control ratio is at or near 1.0 within the profiler's stated measurement uncertainty.
  - **INCONCLUSIVE** records when the profiler produces evidence on both sides (for example, ALU pressure present but bandwidth already at the control ratio; or the control cannot be run for the chosen shape) and a defensible verdict is not derivable from the recorded evidence.
  - **BLOCKED-ON-TOOLING** records when the configured CUDA/ROCm host does not have any version of `ncu`/`nv-nsight-cu-cli`/`nsys` (CUDA) or `rocprof`/`rocprofv3`/`omniprobe` (ROCm) installed; the implementer records the host alias and the probing command that produced the empty result. BLOCKED-ON-TOOLING is not a successful falsification and does not satisfy the task; it is a blocker for the user/integrator to provision tooling.
- **Follow-up recommendation (only on CONFIRMED).** The completion evidence additionally states a concrete follow-up recommendation for a separate task: which specific remediation track (per-plane base offset precomputation, identical-spec straight-word specialization, fixed-bits strength reduction — the three review-recommended tracks) the evidence supports as highest-leverage, the specific shape/dtype tuples the evidence names as the binding case, and the post-blocker touchpoints (`src/shared/standard_tiled_copy.inl` for any kernel-body or metadata change; `src/cuda/copy.cu` and `src/rocm/copy.hip` for any queue-side branching) where the recommended task would land.
