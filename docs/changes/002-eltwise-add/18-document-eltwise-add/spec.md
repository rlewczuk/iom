# Document final elementwise-add contract

**Order:** 18
**Priority:** P2 — required finishing documentation and public-contract alignment after cross-backend coexistence is proven.
**Blocked by:** `17-verify-add-coexistence`
**Source:** `docs/changes/002-eltwise-add/spec.md`

## Outcome

The final ADD behavior is documented consistently in `docs/ARCHITECTURE.md`, `docs/BACKEND_CONTRACT.md`, `README.md`, relevant public-header comments, and the conformance source-map/table sections. The documentation describes the shipped public declarations and tested behavior, removes stale opt-in/throwing-ADD and narrow-TTNN claims, and introduces no public capability knob or alternate ADD API.

## Scope

- Align the architecture and backend-contract descriptions with the exact public OID API produced by the prerequisite migration and the final ADD declaration:
  `oid add(const TensorView& lhs, const TensorView& rhs, TensorView& out) noexcept;`
  It has exactly three `TensorView` parameters, is a common non-virtual facade, and has no `EltwiseOpOptions`, options argument, signature knob, `add_support`, or equivalent capability query. `add` itself is the sole ADD support signal: accepted work returns a positive token; a rejected request returns a negative `OidError` value.
- Document the final public OID definition and token encoding wherever the queue/API contract is described: `using oid = std::int64_t`; `OidError::InvalidArgument = -1`, `Unsupported = -2`, `Overflow = -3`, `ResourceExhausted = -4`, `DeviceError = -5`, and `InternalError = -6`; all negative values are errors, zero is invalid, and positive values are tokens. Preserve all queue IDs `q` in `[1,255]` in bits 55 through 62 with a 55-bit sequence in `[1, 2^55-1]`, using `token = static_cast<oid>((std::uint64_t{q} << 55) | sequence)`; sequence exhaustion is synchronous `Overflow`. The common OID-returning facade is `noexcept`, maps synchronous failures uniformly, and never lets a synchronous exception cross the public operation.
- Document the exact OID error boundary and precedence. Validate device identity, owners, recognized specs, shapes, views, checked arithmetic, and aliasing before effects or token acceptance. A mismatch among recognized leaf types or quantization formats is `InvalidArgument`; only after all three recognized specs match, a common `BOOL`, `F8_E8M0`, or recognized non-`NONE` quantization is `Unsupported`. Other malformed/unknown specs and device, shape, view, or alias errors are `InvalidArgument`; checked arithmetic overflow is `Overflow`; pre-acceptance temporary/metadata/staging/resource allocation failure is `ResourceExhausted`; pre-acceptance backend failure is `DeviceError`; and otherwise unclassified internal failure is `InternalError`.
- State that with `QuantizationFormat::NONE`, CPU, CUDA, ROCm, SYCL, and TTNN each accept all 21 numeric leaves individually, exactly:
  `I2`, `U2`, `I4`, `U4`, `I8`, `U8`, `I16`, `U16`, `I32`, `U32`, `I64`, `U64`, `F4_E2M1`, `F6_E2M3`, `F6_E3M2`, `F8_E4M3FN`, `F8_E5M2`, `F16`, `BF16`, `F32`, and `F64`.
  `BOOL` and `F8_E8M0` are excluded from ADD. Every non-`NONE` quantization remains invalid/out of scope, and a required numeric leaf is not `Unsupported` merely because a vendor SDK lacks native support.
- Describe ADD shape semantics: ranks below two are invalid; `[1,1]` is the only scalar convention and broadcasts over every output axis, while two `[1,1]` operands produce `[1,1]`. For ranks at least two, right-align ranks and conceptually prepend ones; each axis must be equal or one, the result axis is the maximum, and `out` must have exactly that shape. Singleton coordinates, including final tiled rows/columns and tails, map to zero. Resolve logical coordinates before standard/native tile-slot mapping and never read padding. Broadcast materialization is internal only; no public zero-stride view is exposed. Existing transformed leading views retain independent offsets and plane strides for each input and output.
- Document numerical semantics without adding promotion or quantization behavior: all three public specs have the same leaf and there is no promotion. Signed integers use two's-complement and unsigned integers ordinary binary interpretation; output is the low `w` bits of the exact sum modulo `2^w`, never saturating or undefined. Floating values decode by their named format, sum as exact reals, and encode once with RNE; a backend may return the reference encoding or a finite encoding within one ULP. Include the required F4/F6 OCP MX scalar tables, E4M3FN saturation/NaN, E5M2 infinity, IEEE F16/F32/F64, and BF16 special-value rules; gradual underflow and no FTZ/DAZ; exact zero-sign rules; NaN/infinity classes; canonical reference NaN encodings; and the definition of one ULP from the source specification. The OCP MX v1.0 reference link remains normative where applicable, subject to the explicit ADD policies.
- Document aliasing and capture rules: `lhs` and `rhs` may overlap arbitrarily; validate each input against `out`. Same-owner exact in-place alias is allowed only when spec, plane offset, plane strides, and logical element mapping are identical, so the aliased input is not broadcast. Reject every other same-owner input/output relationship, including disjoint windows, broadcast windows, and other non-identical windows, with `InvalidArgument` before submission. Capture both input values before each output store, track all three owners through completion, deduplicate exact aliases, and snapshot view metadata rather than retaining caller view objects.
- Align queue and lifetime documentation with the migrated OID contract: accepted ADD work is in-order asynchronous work (CPU may complete inline), has a positive token, preserves caller serialization and ordering, and supports repeat waits. Invalid negative, zero, foreign, future, skipped, or otherwise unsubmitted values are rejected by `wait`; an accepted asynchronous failure is retained and rethrown on every later wait. Pre-submit failures produce a negative OID, do not mutate output, and do not consume/accept a token; partial output after an accepted failure is unspecified. Keep sequence and queue-ID behavior consistent with the final OID declaration rather than the stale 56-bit/throwing description.
- State that ADD never allocates operands or the result and never replaces, relocates, or changes caller-created storage, owners, or native handles. Caller-owned devices, stable tensor owners/handles, and required owner lifetimes remain in force. Backend-internal temporary host/device buffers, backend tensors, broadcast materialization, workspace, staging, implicit conversions, unpack/widen/repack, and emulation are permitted when needed; their allocation and cleanup stay internal. Path selection is internal before acceptance, no accepted native failure is retried, and no generic fallback subsystem, CPU fallback device/tensor/queue, vendor type, backend-kind switch, or global backend state is exposed by common code.
- Update TTNN documentation to say that its storage/backing, logical transfers, copy, and ADD cover `BOOL` plus all 21 required numeric `NONE` leaves. TTNN need not store `F8_E8M0`; it must preserve public logical shape and ownership semantics while using its native 32x32 per-plane layout and any required internal staging/emulation. Remove wording that limits TTNN to its former eight numeric leaves or treats the narrow table as the final ADD matrix.
- Update the conformance source map/table to identify the final public declarations, independent scalar reference/oracle, shared ADD cases, per-backend full 21-leaf coverage, transformed/broadcast/tiled cases, alias/ownership/lifetime/error cases, and the cross-backend coexistence scenario. Keep common code backend-neutral and identify the exact test source and landed scenario symbols after `17-verify-add-coexistence`; do not document a weaker subset or a new capability framework. The source map must distinguish backend-local execution proof from the sole genuinely cross-backend integration proof.
- Update README support and test descriptions, including the TTNN capability statement and focused conformance/coexistence references, so they agree with the final tables and declarations. Documentation must not claim support for other operations, promotion/quantization, benchmarks, or future behavior.

## Requirements

- All prose, tables, comments, declarations, and source-map entries must describe one consistent final contract. Where a final declaration or scenario name differs from the current repository snapshot, document the final landed form after blockers complete rather than preserving stale text.
- The exact ADD declaration is `oid add(const TensorView& lhs, const TensorView& rhs, TensorView& out) noexcept;`; no fourth parameter, options object, `add_support`, capability query, public fallback selector, promotion control, or quantization codec may be documented or introduced.
- Documentation must state that `add` itself communicates support through a positive token or the specified negative `OidError`, with matching-spec `BOOL`, `F8_E8M0`, and recognized non-`NONE` cases returning `Unsupported` only after mismatch checks; mismatched recognized specs return `InvalidArgument`.
- Documentation must list all 21 required numeric `NONE` leaves verbatim and require them on every CPU, CUDA, ROCm, SYCL, and TTNN backend. It must separately state `BOOL` preservation and TTNN's lack of an F8_E8M0 storage requirement.
- Documentation must preserve exact broadcast, transformed-leading-view, final-tiled-axis/tail, integer modulo, bounded-floating, alias, metadata-snapshot, three-owner tracking/deduplication, asynchronous wait/failure, stable caller storage, and internal staging/emulation semantics from the source specification.
- The final conformance source map/table must cite the independent scalar reference and physical storage oracle, all five backend conformance sources, and the coexistence source/target. It must show that each backend proves its own full behavior and that coexistence is only cross-backend integration.
- Remove stale opt-in throwing ADD wording and former narrow-TTNN capability wording from every in-scope documentation/header location. Do not change behavior, tests, implementation, or unrelated operation documentation beyond correcting directly conflicting shared contract prose.
