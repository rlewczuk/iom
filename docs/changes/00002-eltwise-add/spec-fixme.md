Remarks regarding current design:
* handling `BFLOAT4_B` and `BFLOAT8_B` for TTNN seems to make things too complex as they have to behave like quantizations rather than leaf datatypes; please remove support for those datatypes and all complexities they introduced to the spec (eg. block format section); provide me with viable options how to replace them (eg. remove completely or emulate other types) and ask me which one will be suitable;
* look if there are other significant divergences between TTNN and other backends, 
* as `add()` will be (kind of) low level operation, consider extending `add()` function signature with additional argument that will steer certain aspects of it (eg. broadcasting behavior, math fidelity, some backend-specific behaviors like ttnn memory behavior, optimizations etc.); start with deciding if there are any such out-of-band settings that are necessary, if you find some, then we need additional argument (kind of 'EltwiseOpOptions` struct or something similar); if there are none, then additional parameter is not needed and we don't need to change function signature
* ensure that broadcasting also works if an argument is scalar (or `[1x1]` tensor) -- effectively this is performing scalar operation on a tensor;
* make CPU fallback uniform across all backends, not only specific to TTNN (albeit TTNN has most use of it); if a backend does not need any fallbacks, then it will have none in its implementation but fallback sill still remain a part of formal specification (contract)
* reserve negative range of OIDs to signal errors instead of throwing exceptions, create dedicated header file declaring oid type and enum indicating typical errore (eg. not implemented, device error, etc.)
